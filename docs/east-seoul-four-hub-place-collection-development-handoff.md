- Backend: `D:\Backend\NoPlan`

- 기존 데이터: 성수 후보 69곳과 네이버 메뉴 1,248개를 보존하여 이어서 사용
- 기준 문서: `docs/seongsu-naver-menu-enrichment-implementation-result.md`

## 1. 개발 페이지에 그대로 전달할 요청

아래 문서를 단일 기준으로 Frontend와 Backend를 구현하고 실데이터 수집까지 진행해줘.

기존 `region_key='seongsu'`를 성수역 한 곳이 아니라 성수역·서울숲역·건대입구역·뚝섬역을 포함하는 **성수권 서비스 권역**으로 확장한다. 네 역을 각각 수집 거점으로 사용하고, 현재 NoPlan의 전체 카테고리와 소분류별 장소를 수집한다.

장소는 우선 카카오맵 별점 3.5 이상·후기 10개 이상을 적용하고, 네이버 지도에서 실제 존재 및 운영 여부가 확인된 경우에만 저장한다. 음식점·카페·술집은 현재 구현된 네이버 상세 메뉴 수집까지 연속 실행한다. 각 거점·소분류별 30곳을 목표로 하되, 정상 조건으로 부족한 소분류만 별점 3.0 이상·후기 10개 미만까지 완화한다. 완화 후에도 실제 장소가 부족하면 30곳 미만을 허용하고 부족 수량과 검색 소진 근거를 결과 문서에 기록한다.

Redtable, 소상공인 상가업소, 행정안전부 일반음식점 연동은 기본 흐름에서 완전히 제거하거나 비활성화한다. 네이버 메뉴 수집에 사용하는 공통 Apify 실행기와 `noplan_candidate_external_matches`는 제거하면 안 된다.

수집 결과가 후보 DB에만 머물러서는 안 된다. 자동 품질 조건을 통과한 장소는 관리자 검수·승인 흐름을 거쳐 실제 `noplan_places`에 활성화하고, 성수역·서울숲·건대입구·뚝섬 요청으로 코스를 생성했을 때 승인 장소가 실제 반환되도록 홍대 전용 제한도 함께 수정한다.

한 번의 장시간 HTTP 요청으로 전체 작업을 처리하지 말고 재개 가능한 수집 작업 또는 CLI 스크립트로 구현한다. 5곳 표본 검증 후 전체 실행하고, 거점·카테고리·소분류·품질 단계별 수집/승인/부족 현황과 Apify 사용량을 결과 문서로 남긴다.

## 2. 이번 작업의 최종 목표

최종 사용자 관점에서 다음 지역명을 입력하거나 현재 위치가 인접해 있을 때 NoPlan 코스 추천을 사용할 수 있어야 한다.

```text
성수역
성수동
서울숲
서울숲역
뚝섬
뚝섬역
건대
건대입구
건대입구역
화양동
자양동
```

필수 데이터 흐름:

```text
카테고리·소분류별 카카오맵 후보 수집
→ 카카오 별점·후기 조건 적용
→ 거리 및 장소 유형 검증
→ 네이버 지도 존재·운영 여부 교차검증
→ 후보 저장 및 품질 단계 기록
→ 음식·카페·술/야간 후보의 네이버 상세 메뉴 수집
→ 관리자 검수 및 승인
→ 실제 코스 생성에서 승인 카탈로그 사용
```

## 3. 권역 모델

### 3.1 `seongsu`는 하나의 서비스 권역으로 유지

역마다 `region_key`를 새로 만들지 않는다. 기존 69곳과 코스 추천 호환성을 위해 다음 값을 유지한다.

```text
region_key = seongsu
```

대신 권역 안에 다음 네 개의 수집 거점을 둔다.

| hubKey | 표시명 | 기준 좌표(구현 전 Kakao 좌표와 최종 대조) |
|---|---|---|
| `seongsu_station` | 성수역 | 37.544581, 127.055961 |
| `seoul_forest` | 서울숲역 | 37.5436, 127.0447 |
| `konkuk_univ` | 건대입구역 | 37.5404, 127.0692 |
| `ttukseom` | 뚝섬역 | 37.5472, 127.0474 |

기본 수집 반경은 거점별 1,200m다. 부족한 소분류를 보충할 때만 최대 1,800m까지 넓힐 수 있다.

### 3.2 중복 장소 처리

네 거점의 반경은 서로 겹치므로 같은 장소를 역별 후보 행으로 복제하면 안 된다.

- 장소의 전역 식별자는 기존과 같이 `provider + provider_place_id`를 사용한다.
- `nearest_station`과 `station_distance_m`에는 네 거점 중 실제 최단 거점을 기록한다.
- 커버리지 계산은 장소 좌표와 요청 거점 사이의 실제 거리로 계산한다.
- 한 장소가 두 거점 모두에서 1,200m 이내라면 두 거점의 서비스 커버리지에는 포함될 수 있다.
- DB 장소 행, 메뉴, 이미지, 승인 행은 한 번만 저장한다.
- 같은 장소를 다른 거점에서 다시 발견하면 `region_key`나 승인 상태를 덮어쓰지 말고 수집 이력만 추가한다.

## 4. 수집할 현재 NoPlan 분류

Frontend의 현재 `DETAIL_OPTIONS`와 서비스 분류를 기준으로 한다. Frontend와 Backend가 서로 다른 목록을 갖지 않도록 공통 분류 정의를 한 곳에서 관리하거나 회귀 테스트로 동일성을 보장한다.

| 대분류 | 내부 분류 | 소분류 |
|---|---|---|
| 맛집 | `food` | 해산물, 고기, 한식, 일식, 중식, 양식, 분식, 기타 음식 |
| 카페/디저트 | `cafe` | 커피, 디저트, 베이커리, 브런치, 기타 카페 |
| 놀거리 | `activity` | 공방/체험, 방탈출, 보드게임, 볼링, 노래방, 오락실, 스포츠, 서브컬쳐 |
| 문화/전시 | `culture` | 전시, 영화, 공연, 팝업, 미술관/박물관, 독립서점, 복합문화공간 |
| 술/야간 | `drink` | 펍, 포차, 와인/칵테일, 이자카야, 기타 술집 |
| 산책/구경 | `walk` | 산책, 공원, 야경, 쇼핑몰, 시장/상권, 기타 명소 |

총 39개 소분류다. 목표치만 단순 계산하면 `4개 거점 × 39개 소분류 × 30곳`이지만, 이는 4,680개의 중복 없는 가게 행을 만들라는 의미가 아니다. 반경이 겹치는 장소는 여러 거점 커버리지에 포함할 수 있으며, 실제 공급이 부족한 분류는 30곳 미만을 허용한다.

### 4.1 `primary_type` 호환

현재 DB 구조와 코스 로직의 호환을 위해 다음 매핑을 유지한다.

```text
맛집       → food
카페/디저트 → cafe
놀거리     → activity
문화/전시   → activity
술/야간     → drink
산책/구경   → hotplace
```

`문화/전시`와 `놀거리`, `산책/구경`은 `primary_type`만으로 구분하지 말고 정규화된 `detail_type`을 함께 사용한다. 원본 카카오 분류는 `category_raw`, `category_path_raw`에 보존한다.

## 6. 품질 조건과 완화 순서

### 6.1 1단계: 기본 조건

모든 소분류는 먼저 아래 조건으로 수집한다.

```text
카카오맵 별점 >= 3.5
카카오맵 후기 수 >= 10
별점과 후기 수가 모두 실제 숫자로 존재
거점 반경 <= 1,200m
네이버 지도 운영 장소 매칭 성공
```

이 조건을 `quality_tier=A`로 기록한다.

### 6.2 2단계: 부족할 때만 완화

1단계 결과가 해당 거점·소분류에서 30곳 미만일 때만 추가 수집한다.

```text
카카오맵 별점 >= 3.0
카카오맵 후기 수 >= 0
별점은 반드시 존재
거점 반경 <= 1,200m
네이버 지도 운영 장소 매칭 성공
```

이 조건을 `quality_tier=B`로 기록한다. 후기 10개 이상인 장소도 기본 단계에서 누락됐다면 B단계로 들어올 수 있지만, 정렬 우선순위는 A단계보다 낮아야 한다.

### 6.3 3단계: 거리만 확대

B단계까지 실행해도 30곳 미만인 소분류만 반경을 최대 1,800m로 확대한다. 별점 3.0 미만 또는 별점이 없는 장소는 추가하지 않는다.

```text
quality_tier=C
quality_exception_reason=scarce_category_radius_expanded
```

### 6.4 끝까지 부족한 경우

검색어와 반경 확대를 모두 소진했는데 실제 장소가 부족하면 그 수량 그대로 종료한다.

- 30곳을 맞추기 위해 잘못된 소분류를 넣지 않는다.
- 별점 3.0 미만 장소를 넣지 않는다.
- 폐업·운영 종료·지점 불일치 장소를 넣지 않는다.
- 같은 장소를 복제해 숫자를 채우지 않는다.
- 결과에 `shortage=true`, 확보 수, 부족 수, 마지막 적용 단계, 검색어별 원본/탈락 수를 기록한다.

## 7. 소분류 판정 규칙

현재 `inferDetailType()`만으로는 브런치·독립서점·복합문화공간·산책·공원·야경·쇼핑몰·시장/상권 등을 충분히 분류하지 못한다. 전체 39개 분류를 지원하도록 Backend 분류기를 확장한다.

판정 우선순위:

1. 수집 작업이 요청한 소분류
2. 카카오 `categoryPath`
3. 카카오 상세 카테고리와 상호명
4. 네이버 카테고리
5. 모호하면 `review_required`

요청 소분류만 믿고 강제 저장하면 안 된다. 예를 들어 `성수역 전시` 검색에서 카페가 나온 경우 카페로 재분류하거나 제외해야 한다.

한 장소는 서비스의 대표 소분류 하나만 갖는다. 검색어가 달라도 같은 장소가 여러 소분류에 중복 집계되지 않도록 한다.

## 8. 네이버 존재·운영 교차검증

기존 카카오 후보와 네이버 결과 매칭 기준을 유지한다.

자동 통과 우선순위:

1. 네이버 장소 ID 또는 URL 완전일치
2. 전화번호 완전일치와 호환되는 상호명
3. 상호명 완전일치와 도로명주소 일치
4. 상호명 완전일치와 좌표 100m 이내

다음 상태는 저장 또는 승인하지 않는다.

```text
폐업
영구 폐쇄
운영 종료
다른 지점
동명이지만 주소·전화·좌표 확인 불가
네이버 검색 결과 없음
```

현재 `findPlaceOnNaver()`의 허용 거리가 일부 250~600m로 넓으므로, 네이버 상세 메뉴 수집 때 사용하는 더 엄격한 지점 매칭 기준과 통합하거나 최종 저장 전 다시 검증한다.

## 9. 메뉴 자동수집

### 9.1 메뉴 수집 대상

다음 분류는 네이버 교차검증 직후 현재 구현된 메뉴 상세수집을 자동 실행한다.

```text
food
cafe
drink
```

`activity`, `culture`, `walk`는 메뉴가 없을 수 있으므로 메뉴 0개가 정상이다. 단, 체험 가격이나 이용권 정보가 네이버 `MenuItems`로 제공되면 후보 메뉴로 저장할 수 있다.

### 9.2 기존 구현 재사용

- Actor: `delicious_zebu~naver-map-search-results-scraper`
- `scrapePlaceDetails: true`
- 메뉴 배열: `MenuItems`, `menuItems`, `menus`, `menu`
- 메뉴 출처: `apify_naver_menu`
- 24시간 캐시, 재시도, 멱등성, 수동 메뉴 보호 정책 유지
- 메뉴명·숫자 가격·가격 원문 정규화 유지

현재 `naverMenuProvider.js`의 키워드 fallback에 `성수역`이 하드코딩되어 있다. 다음처럼 후보의 실제 최단 거점을 사용하도록 수정한다.

```text
${candidate.nearest_station} ${candidate.name} ${candidate.road_address}
```

`naverMenuService.js`의 `candidate.region_key !== 'seongsu'` 제한은 성수권 전체에 대해 계속 허용되므로 기존 `seongsu` 값이면 정상 처리한다. 역 이름으로 제한하면 안 된다.

### 9.3 서비스 노출 조건

- `food`, `cafe`, `drink`: 네이버 장소 매칭 성공 후 메뉴 수집을 반드시 한 번 실행한다.
- 메뉴가 있으면 활성 메뉴를 저장한다.
- 실제 네이버에 메뉴가 없는 경우 `no_menu`를 기록하고 관리자 검수 대상으로 둔다.
- 자동 메뉴 수집 오류가 난 후보는 성공으로 집계하거나 자동 승인하지 않는다.
- 메뉴 없는 놀거리·문화·산책 장소는 메뉴 때문에 탈락시키지 않는다.

## 10. Redtable·상가업소·일반음식점 제거

- 후보 공공데이터 보강 API
- 외부 동기화 상태 API 중 위 세 Provider 전용 기능

## 11. 대량 수집 작업 구조

전체 조합을 하나의 HTTP 요청으로 실행하면 타임아웃과 중간 실패 복구 문제가 생긴다. 기존 수집 코드를 서비스 함수로 분리하고 다음 중 하나 이상을 제공한다.

```text
Backend 재개 가능 collection job
또는
scripts/collectSeongsuAreaCatalog.js --resume
```

권장 실행 단위:

```text
거점 1개 × 소분류 1개 × 품질 단계 1개
```

필수 기능:

- 체크포인트와 `--resume`
- 이미 목표 30곳을 충족한 조합 건너뛰기
- 카카오 장소 ID 전역 중복 제거
- 같은 네이버 장소의 반복 상세조회 방지
- 후보별 실패 격리
- 429·5xx 지수 백오프
- 동시 실행 제한
- 실행 중단 후 재개 시 중복 메뉴/후보 미생성
- 작업별 Apify run ID, 사용 결과 수, 오류 기록
- 원본 수, A/B/C 통과 수, 네이버 미확인 수, 메뉴 성공 수 기록

관리자 API를 추가한다면 예시는 다음과 같다.

```http

GET  /api/admin/places/collection-jobs/:jobId
```

요청 예시:

```json
{
  "regionKey": "seongsu",
  "hubKeys": ["seongsu_station", "seoul_forest", "konkuk_univ", "ttukseom"],
  "targetPerDetail": 30,
  "primaryRule": { "minRating": 3.5, "minReviewCount": 10, "radius": 1200 },
  "fallbackRule": { "minRating": 3.0, "minReviewCount": 0, "radius": 1200 },
  "expandedRadius": 1800,
  "collectMenus": true
}
```

## 12. 기존 69곳 처리

기존 성수 69곳과 네이버 메뉴 1,248개는 다시 만들지 않는다.

1. 좌표를 기준으로 네 거점까지의 거리를 다시 계산한다.
2. `nearest_station`, `station_distance_m`를 실제 최단 거점으로 보정한다.
3. 기존 정규 소분류가 없거나 잘못된 후보만 재분류한다.
4. 기존 `apify_naver_menu` 메뉴는 유지한다.
5. 후보와 메뉴의 카카오·네이버 ID가 같으면 신규 수집 결과와 병합한다.
6. 승인된 기존 장소가 있다면 승인 상태를 유지한다.

## 13. 실제 서비스 지원 수정

현재 `routes/course/courseLocation.js`의 `CATALOG_REGIONS`에는 홍대만 있으며, 코스 생성에는 `requestedRegionKey !== 'hongdae'` 차단 코드가 있다. 장소 수집만 늘리고 이 부분을 두면 성수권에서 서비스가 계속 실패한다.

반드시 다음을 수정한다.

- `CATALOG_REGIONS.seongsu` 추가
- 성수권 서비스 중심 및 반경 추가
- 성수역·서울숲·뚝섬·건대입구 위치 힌트 추가
- 텍스트 지역 판정에 `서울숲`, `뚝섬`, `건대`, `화양`, `자양` 추가
- `catalogOnly`의 홍대 전용 차단을 지원 권역 목록 검사로 변경
- 성수권 요청이면 `region_key='seongsu'` 승인 장소 조회
- 요청한 역 좌표를 코스 anchor로 사용
- 추천 후보를 anchor와의 실제 거리로 필터·정렬
- 코스 이동거리가 지나치게 길어지지 않도록 기존 거리 제한 적용
- 오류 문구를 홍대 전용 안내에서 현재 지원 권역 안내로 변경

지원 권역 검사는 하드코딩 비교 대신 다음 형태를 사용한다.

```text
Boolean(CATALOG_REGIONS[requestedRegionKey])
```

## 14. 관리자 화면 변경

기존 지역 선택에서 `성수역` 단일 버튼을 다음처럼 표시한다.

```text
성수권
```

성수권 내부 필터:

```text
전체 | 성수역 | 서울숲역 | 건대입구역 | 뚝섬역
```

커버리지 화면은 다음 열을 제공한다.

```text
거점
대분류
소분류
목표 수
A단계 수
B단계 수
C단계 수

승인·활성 수

```

후보 카드에는 `A`, `B`, `C` 품질 단계와 완화 사유를 표시한다. B/C 후보는 관리자가 구분할 수 있어야 한다.

네이버 메뉴 단건·선택 일괄 버튼은 성수권 네 거점 모두에서 보이게 한다. 기존처럼 `regionKey === 'seongsu'` 조건을 사용할 수 있지만 특정 역 이름으로 제한하지 않는다.

## 15. 승인 및 서비스 반영

수집 후보 수와 실제 서비스 장소 수를 혼동하지 않는다.

```text
후보 수 = noplan_place_candidates
서비스 노출 수 = noplan_places WHERE is_active=1
```

자동 승인 가능한 최소 조건:

- 카카오 장소 ID 존재
- 품질 A/B/C 중 하나 충족
- 네이버 운영 장소 매칭 성공
- 주소 또는 좌표 존재
- 정규 대분류·소분류 확정
- 중복 장소 아님
- 음식·카페·술집은 네이버 메뉴 수집 실행 완료
- 자동수집 오류 없음

`review_required`, 지점 불명확, 소분류 모호, 메뉴 수집 오류 후보는 자동 승인하지 않는다.

대량 승인 전 거점별·대분류별 표본을 확인한다. 자동 승인 기능을 구현할 경우 실행 결과와 되돌릴 수 있는 승인 batch ID를 기록한다.

## 16. API·DB 권장 변경

### 16.1 품질 단계 저장

후보와 승인 장소에 다음 값을 영속적으로 남긴다. 기존 `raw_payload`에만 넣고 끝내지 않는다.

```text
quality_tier VARCHAR(10) NULL
quality_exception_reason VARCHAR(120) NULL
```

기존 69곳은 원래 조건이 별점 3.5·후기 10개 이상이므로 검증 후 `A`로 보정한다.

### 16.2 커버리지 API

기존 `/coverage`의 부족 기준은 소분류별 3곳으로 하드코딩되어 있다. 거점과 실제 거리 기준으로 계산하도록 확장한다.

```http
GET /api/admin/places/coverage?regionKey=seongsu&hubKey=seoul_forest&target=30
```

`shortage`는 승인·활성 장소가 30곳 미만일 때 `true`다. 후보 수와 승인 수를 별도로 반환한다.

- 기존 성수 69곳과 네이버 메뉴 1,248개가 손실·중복 없이 보존된다.
- 성수역·서울숲역·건대입구역·뚝섬역 네 거점에서 전체 39개 소분류 수집을 실제 실행한다.
- 모든 저장 후보가 카카오 품질 A/B/C 중 하나와 네이버 운영 매칭을 갖는다.
- A단계를 먼저 사용하고 부족한 조합에만 B/C단계를 사용한다.
- 각 거점·소분류별 승인 장소 30곳을 목표로 한다.
- 30곳 미만인 조합은 검색 소진과 실제 확보 수가 결과 문서에 명시되어야 한다.
- 부족한 숫자를 채우기 위한 중복·오분류·기준 미달 장소가 없다.
- 음식·카페·술집은 네이버 메뉴 수집을 실제 실행하고 성공·메뉴 없음·오류 수를 보고한다.
- 후보뿐 아니라 승인·활성 장소 수를 별도로 보고한다.
- 네 지역명으로 코스 API를 호출했을 때 `unsupported_region`이 나오지 않는다.
- 각 지역 코스에 성수권 승인 카탈로그 장소가 실제 포함된다.
- Backend 전체 테스트와 Frontend 빌드가 통과한다.
- 최종 결과 문서에 거점×대분류×소분류별 A/B/C/승인/부족 수와 Apify 사용량·예상 비용을 제공한다.

## 20. 결과 문서 필수 표


## 21. 사용 환경변수

새 API 키는 필요 없다. 현재 사용하는 다음 값만 유지한다.

```text
KAKAO_REST_API_KEY
APIFY_API_TOKEN
NOPLAN_ADMIN_KEY
```

API 토큰과 관리자 키는 로그·결과 문서·Frontend 번들에 노출하지 않는다.
