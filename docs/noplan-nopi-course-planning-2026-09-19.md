# 노피의 코스플래닝 — 울산 시범 구현

## 사용자 흐름

- 울산 여행의 날짜별 상단: **노피의 코스플래닝**, **하루 동선 보기**. 별도의 직접 코스 짜기 버튼은 제거했다.
- 자동: 출발/종료 시간, 도보/차량, 여행 목적, 권역, 회원 연령·성별 또는 직접 선택한 추천 기준 → 미리보기 → 장소 교체/순서/체류시간 수정 → 이날 반영.
- 생성 후 기존 일정 카드 또는 노피의 코스플래닝에서 장소를 추가·교체·수정한다. 한 장소를 한 일정 구간으로 저장한다.
- 일정 카드와 전체 일정에 장소 사진을 표시한다. 저장된 울산 일정도 contentId로 공개 사진을 불러오며, 사진이 없으면 준비 중으로 표시한다. 보라색 구간 설명은 제목·주소와 정렬한다.
- 일정의 성·연령 방문 비중 문구는 표시하지 않는다. 기존 저장 메모에서도 해당 자동 생성 문구만 표시 시 숨기고, 추천 점수 계산은 유지한다.
- 첫날 반영 후 다음 날로 바로 이동한다. 여행 전체에서 이미 담은 관광공사 contentId는 선택 목록에서 비활성화한다.
- 마지막 날은 반영 후 전체 일정 보기로 이어진다. 전체 보기에서는 각 날짜 수정과 하루 동선 보기로 이동할 수 있다.
- 기존 ‘이 구간 채우기’는 계속 숨김. 모바일 주변 코스 기능 자체는 유지한다.
- 미리보기는 `http://localhost:5173/dev-preview/nopi-planner.html` (로컬 API 4318, 샘플 20대 여성, 운영 DB 미연결).

## 추천·시간 계산

- 관광공사 울산 공개 장소 389곳, 소개정보 372곳을 이용한다. 음식점 115곳 포함. 소개정보 15곳 실패, 여행코스 2곳은 소개정보 수집 제외.
- 추가 GET `/api/tourism/nopi-catalog`: 기존 회원 인증 정보로 연령·성별을 구하고 공개 후보와 연결한다. 생년월일/회원 ID/원본 성·연령 배열은 응답하지 않는다. `private, no-store`.
- 통계가 있는 장소만 방문 비중/검색건수를 점수에 반영한다. 목적은 장소 분류·이름·메뉴에 따른 규칙 기반이며, 목적별 실제 방문 통계라고 표시하지 않는다.
- 여러 출발 권역을 남기는 빔 탐색으로 목적·통계 점수와 거리를 함께 비교한다. 최적해를 보장하는 TSP 솔버는 아니다.
- 도보는 다음 후보까지 직선 1.6km, 차량은 16km 이내에서 연결한 뒤 실제 이동을 검증한다. 실제 도보 40분/차량 60분을 넘는 연결은 제외하고 최대 3회 탐색한다.
- 기존 POST `/api/tourism/day-route`를 사용한다. TMAP 보행자/카카오 자동차 API 설정, 서버 캐시, 동시성·분당·일일 제한을 그대로 적용한다. 자동차 시간에는 기존 주차 여유가 포함된다.
- 실제 경로 조회가 안 되면 자동 결과를 확정하지 않는다. 직접 편집에서는 미확인 구간의 시간을 사용자가 입력할 수 있고 ‘직접 입력’으로 구분한다.
- 기본적으로 3~6곳을 배치하고 식사 60분, 카페 40분을 배정한다. 카페 정보가 부족할 때 식당으로 가장하지 않는다. 여러 장소를 묶은 여행코스(25), 등산·캠핑·계절성 물놀이 등은 자동 후보에서 제외한다. 직접 담기는 가능하다.
- 명확한 운영 시작/종료, 브레이크타임, 매주/매월 정기 휴무를 검사한다. 계절별·조건부·모호한 안내, 임시 휴무, 예약 가능 여부는 검증 완료로 표시하지 않는다. 방문 전 확인 안내를 유지한다.
- 출발지(숙소/역)부터 첫 장소, 마지막 장소부터 숙소 이동은 이번 범위에 포함하지 않는다.
- 예산/가격 검증은 이번 자동 코스에서 제외한다.

## 저장과 호환성

- 기존 TripDocument의 날짜·구간·장소 구조를 재사용한다. DB 테이블/컬럼 추가 없음.
- `days[].transport` 선택 필드를 추가했다. 없는 기존 문서는 여행 기본 이동수단을 사용한다. 첫날 차량/둘째 날 도보를 독립적으로 저장한다.
- 해당 날짜만 교체하고 다른 날짜는 보존한다. 반영 전 기준 문서 비교, 저장/동기화 중 반영 차단, 기존 되돌리기·공동편집을 유지한다.
- 관광지 교체 시 전체 날짜의 중복 contentId를 확인한다. 기존에 이미 중복이 있는 여행은 새 코스 반영 시 중복을 해소해야 한다.
- 장소 메타데이터와 직접 입력한 메모를 유지한다. 기존 여러 장소를 한 구간에 담은 날은 직접 코스 반영 시 한 장소씩 구간을 나눈다. 변경 안내를 확인한 뒤 반영한다.

## 배포

백엔드를 먼저 배포하고 프론트엔드를 배포한다. 기존 음식점 추가 작업도 함께 필요하다.

새 백엔드 파일:

- `routes/tourism/nopiCatalog.js`
- `data/tourism/ulsan-planning-facts.json` **배포에 반드시 포함**
- `scripts/fetch-ulsan-planning-facts.cjs` (관리자 로컬 갱신용, 서비스 실행 중 자동 수집하지 않음)
- `tests/nopiCatalog.test.js`

변경 백엔드 파일: `routes/tourism/router.js`, `routes/trips/validation.js` 및 앞선 음식점 지원 변경. 새 유료 API/키/구독은 추가하지 않았다. 기존 `TMAP_APP_KEY`, 카카오 경로 키 설정을 유지한다.

공개 소개정보 갱신: 백엔드에서 `node scripts/fetch-ulsan-planning-facts.cjs` 실행 후 데이터 파일을 배포하고 프로세스를 재시작한다. 200곳 미만 성공하면 기존 파일을 덮어쓰지 않는다. 자격증명은 로그에 출력하지 않는다.

## 확인 결과

- 프론트 빌드 성공. 관련 프론트 테스트 24개, 백엔드 관광지·경로·일정 테스트 38개 통과.
- 실제 API 통합: 첫날 자동차 5곳, 둘째 날 도보 5곳 생성 후 백엔드 저장 검증 통과. API 호출 결과에는 `kakao_driving`, `tmap_pedestrian` 출처 확인.
- 브라우저: 첫날 반영 → 다음 날 도보 생성 → 첫날 장소 비활성화 → 중간 장소를 태화루로 교체 → 실제 이동 재조회 → 전체 일정 → 날짜별 지도 확인.
- 코드 린트 오류 없음. 기존 TripWorkspace의 불필요한 eslint-disable 경고 1건과 기존 번들 크기 안내는 남아 있다.

## 이후 API 검토

현재 시범 규모는 기존 구간 경로 조회로 충분하다. 향후 많은 후보 간 **실제 도로 이동시간**을 비교하려면 TMAP 경로 매트릭스, 선택된 여러 장소의 방문순서를 정밀하게 조정하려면 경유지 최적화를 검토한다. 무료 체험/종량제 범위와 계정 계약 조건을 먼저 확인하며 이번 작업에서는 구독을 추가하지 않았다.

- 공식 기능 안내: https://www.tmapmobility.com/support/data/route/about
- 공식 요금 방식 안내: https://www.tmapmobility.com/support/data/route/demo
