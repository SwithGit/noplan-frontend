# NoPlan PC 웹 개발 인수인계

작성일: 2026-09-18 · 대상: 다른 Codex 작업에서 PC 웹 개발을 이어갈 개발자

이 문서는 모바일·공통 추천 알고리즘 작업에서 확정된 기획 의도와 현재 구현을 PC 작업에 전달한다. 새 기능 전체를 한 번에 개발하라는 명세가 아니다. 다음 작업에서 사용자가 지정하는 PC 화면·기능을 개선하되, 아래 공통 정책을 유지한다.

## 1. 먼저 알아야 할 결론

**PC는 여행 전체를 계획·비교·편집하는 화면, 모바일은 가까운 코스를 추천받고 현장에서 실행하는 화면이다. 장소·행사·계정·찜·추천 엔진은 공통으로 사용한다.**

- PC 홈, 내 여행, 개인 여행 편집기, 행사 탐색은 이미 구현돼 있다. 빈 프로젝트처럼 다시 만들지 않는다.
- 이번 대화에서 가장 많이 수정한 영역은 공통 추천 엔진이다. PC UI를 만들면서 예산·시간·산책·저녁 식사 규칙을 별도로 복제하거나 예전 방식으로 되돌리지 않는다.
- 현재 검증된 AI 추천 범위는 **서울·도보**다. 여행을 다른 지역으로 직접 작성할 수 있다는 것과 해당 지역 AI 추천이 지원된다는 것은 다르다.
- 긴 일정은 사용자가 선택한 활동을 먼저 확보하고 남은 시간·예산에 맞춰 채운다. 항상 2곳, 항상 놀거리 2개, 산책을 번갈아 끼우기 같은 고정 패턴을 사용하지 않는다.
- 문화·전시는 일반 코스의 필수 활동과 자동 채움에서 분리했다. 별도 행사 탐색과 코스 주변 행사 안내로 연결한다.
- 영업시간 확인 체크박스는 제거했다. 자동으로 확인하고, 미확인 장소는 안내와 함께 포함하며 확인된 휴무·영업 종료는 제외한다.

### 문서와 코드의 우선순위

이후 사용자의 명시적 변경 지시가 가장 우선한다. 이 문서는 현재까지 확정된 결정을 정리한 기준이며, 실제 작업 시 최신 코드와 동작을 함께 확인한다. 2026-09-16 문서에는 초기 제안과 당시 검증 결과가 섞여 있으므로 현재 정책으로 그대로 복원하지 않는다.

문서 작성 시 확인한 로컬 기준:

| 항목 | 위치 / 상태 |
|---|---|
| 프론트 | `D:/VSCode/NoPlan/noplan-web` · React / TypeScript / Vite |
| 백엔드 | `D:/Backend/NoPlan` · Node.js / Express / MySQL |
| 프론트 HEAD | `bad0fbb` |
| 백엔드 HEAD | `74828f9` |
| 작업 트리 | 작성 시작 시 두 저장소의 `git status --short` 출력 없음 |
| 운영 환경 | EC2, PM2 프로세스명은 사용자 로그에서 `noplan-backend` |
| 배포 확인 | 로컬 반영과 운영 배포는 별개. 이 문서 작성 중 EC2 배포 상태는 확인하지 않음 |

저장소는 분리되어 있다. 새 작업에서는 두 저장소의 최신 상태와 AGENTS.md 등 적용 지침을 다시 확인한다. 이 문서에 API 키나 DB 접속 비밀번호는 포함하지 않는다.

## 2. 제품과 화면의 기획 의도

### PC

- 목적지·날짜를 정하고 여행 전체를 구성한다.
- 장소·코스·행사를 넓은 화면에서 비교하고, 날짜별 시간 구간에 담는다.
- 필요한 구간만 기존 추천 엔진으로 채운다. 추천받을 때 이미 정한 장소와 다른 구간이 사라져서는 안 된다.
- 즉시 주변 추천도 사용할 수 있다. PC라는 이유로 빠른 추천 진입을 없애지 않는다.
- 기획의 기본 정보 구조는 **여행 → 날짜 → 시간 구간 → 장소·행사**다.
- ‘찜’은 후보를 보관하는 기능이고, ‘내 여행’은 실제 편집하는 일정이다.

### 모바일

- 기본 진입은 홈이다. 조건 입력 → 추천 비교 → 선택 → 출발 → 장소 상세·교체가 핵심 흐름이다.
- 하단 메뉴 순서는 **문화·행사 / 탐색 / 홈 / 찜 / 마이**다. 홈은 가운데다.
- 빠른 추천과 자연어 입력을 모두 유지한다.
- 사용자는 화면을 간단히 만드는 것보다 실제로 만족할 만한 추천을 더 중요하게 여긴다. 필요한 예산·취향 입력을 무리하게 숨기지 않는다.

### 현재 디자인 방향

- 노피 캐릭터와 보라색 브랜드를 유지한다.
- 사용자는 정보가 긴 카드 목록으로만 늘어지는 화면보다, 코스 선택 카드와 시간 흐름이 구분되는 카드뉴스 느낌의 구성을 선호했고 최근 결과 화면 시안을 긍정적으로 평가했다.
- 큰 사진·명확한 정보 위계·여백을 활용하되, 예산·이동·체류·확인 필요 상태는 읽기 쉬워야 한다.
- 가격 미확인 후보, 영업·경로 미확인 후보 같은 부가 정보는 접어서 볼 수 있게 한다. 진단 내용이 주 추천보다 더 크게 보이지 않게 한다.
- PC 디자인을 개선할 때 모바일을 단순히 가로로 늘린 화면으로 만들지 않는다. 동시에 공통 상태·요청·결과 모델을 분리 복제하지 않는다.

## 3. 이미 있는 PC 기능

현재 코드 및 기존 구현 문서로 확인한 출발점이다. 이 문서 작성 과정에서 모든 PC 기능을 운영 환경으로 다시 E2E 검증한 것은 아니다.

| 경로 | 역할 |
|---|---|
| `/` | 랜딩 |
| `/app` | PC에서는 여행 계획 홈, 모바일에서는 추천 홈 |
| `/app/quick` | PC에서도 사용할 수 있는 빠른 주변 추천 |
| `/app/trips` | 내 여행 목록 |
| `/app/trips/new` | 여행 생성 |
| `/app/trips/:id` | 날짜·구간·장소 편집 |
| `/app/events` | 축제·전시·행사 탐색 |
| `/app/events/:id` | 행사 상세 |
| `/app/explore` | 여행 탐색 |
| `/app/favorites` | 찜 |
| `/app/planner/*` | 채팅·조건·검색 진행·결과 |
| `/app/course/place/:index` | 장소 상세 |
| `/app/course/replace/:index` | 장소 교체 |

PC 상단 메뉴는 **여행 탐색 / 축제·전시 / 내 여행 / 찜**이며, 우측에 여행 만들기와 로그인·마이 진입이 있다.

기존 개인 여행 편집 기능:

- 1~14일 여행 생성, 목적지·날짜·동행·교통 정보 편집.
- 날짜별 시간 구간 생성·수정·이동·삭제, 구간 겹침 검증.
- 장소 직접 추가, 체류시간·주소·순서 변경, 고정·해제.
- 선택한 구간에 AI 추천 → 미리보기 → 사용자가 적용. 기존 장소 뒤에 추가하며 다른 구간을 보존한다.
- 추천 요청 중 일정이 바뀌면 오래된 추천 결과를 적용하지 못하게 한다.
- 브라우저 초안, 로그인 계정 저장, 저장 버전 충돌 보호.
- 기존 구현 문서에 개인 편집의 최근 20회 되돌리기가 기록돼 있다. 이를 후순위로 미룬 ‘협업 변경 이력’과 혼동해서 삭제하지 않는다.
- 추천 장소 지도 표시, 직접 입력한 장소의 지도 검색 링크.
- 행사 상세에서 여행의 날짜·구간을 골라 담기. 초안 반영과 계정 저장은 구분한다.

여행 API는 `GET /api/trips`, `GET /api/trips/:id`, `PUT /api/trips/:id`를 사용한다. 저장은 소유자 인증과 version 검사를 유지해야 하며, 충돌 시 최신 내용을 조용히 덮어쓰지 않는다.

### 반응형 기반

- PC 기준은 1024px 이상이다. 768~1023px은 태블릿 배치다.
- `/app`의 `HomeEntry`는 PC·모바일 홈을 함께 유지하고 표시만 바꿔 리사이즈 중 입력을 보존한다.
- 브라우저 폭 변경만으로 추천 상태를 초기화하거나 URL을 바꾸지 않는다.
- 공통 레이아웃·색상 변수는 `src/styles/app-layout.css`의 `--np-*`를 확인한다.

## 4. 반드시 유지할 공통 추천 정책

### 4.1 시간과 필수 활동

- 전체 시간은 **종료 시각 - 시작 시각**으로 계산한다. 한국 시간 기준으로 자정 이후 종료도 처리한다.
- 사용자가 선택한 활동은 필수 활동이고, 자동 추가는 별도다. `autoAdded`, `flowRole`, `mealRole`을 화면·교체·저장에서 무시하지 않는다.
- 선택한 유형 1개는 ‘가게 1곳만 방문’이라는 뜻이 아니다. 자동 채우기가 켜져 있다면 해당 조건에 맞춰 추가할 수 있다.
- 자동 채우기 OFF면 자동 장소를 넣지 않는다.
- 현재 자동 편성은 최대 6곳이라는 구현 한계가 있다. 6곳을 항상 채우는 목표가 아니며, 더 긴 여행 전체를 최적화하는 기능도 아니다.
- 남은 시간·예산에 맞는 후보가 없으면 자유시간과 실제 사유를 안내한다. 가짜 장소나 검증하지 않은 완성 일정을 만들지 않는다.

기본 체류 계획값은 식사 약 75분, 카페 120분, 일반 놀거리 약 90분, 술집 약 120분이다. 잔여 시간에 따라 허용 범위에서 줄일 수 있다. 분 표시에는 소수점이 길게 나오지 않도록 한다.

### 4.2 예산

- **전체 코스의 1인 예산**이다. 인원수, 공유 음식, 주류 주문량을 반영한다.
- 예상 최저·최고 가격의 **평균**을 기준으로 예산 적합 여부를 판단한다. 최고 금액이 예산을 넘었다는 이유만으로 탈락시키지 않는다.
- 화면에는 비용 범위와 추정·가정 정보를 보존한다. 평균으로 예산을 맞췄더라도 실제 주문에 따라 초과할 수 있음을 안내한다.
- 예산 0 또는 미지정은 무제한으로 취급하는 백엔드 정책이다. ‘잔액 0원’으로 해석하지 않는다.
- 가격 미확인과 예산 초과는 다른 실패 사유다. 이를 같은 메시지로 표시하지 않는다.
- 필수 활동 조합 자체가 예산을 넘으면, 사용자의 요청에 따라 이미 찾은 적합 후보 1곳을 검증해 부분 추천하는 경로가 있다. 끝없이 더 저렴한 가게를 다시 찾는 방식으로 바꾸지 않는다.
- 이 1곳 처리 전에 불필요한 자동 추가 비용을 먼저 줄인다. 자동 놀거리 때문에 사용자가 선택한 카페를 먼저 빼는 회귀가 있었다.

사용자가 승인한 가격 가정:

| 상황 | 계산 기준 |
|---|---|
| 일반 놀거리의 사용 가능한 가격 자료 없음 | 1인 10,000원 |
| 방탈출의 사용 가능한 가격 자료 없음 | 1인 20,000원 |
| 산책·구경 | 0원 |
| 소주를 취급하는 근거가 있으나 계산 가능한 소주 단가 없음 | 1주문단위 5,000원 |

실제 계산 가능한 가격이 있으면 그 자료를 우선한다. 소주 가정을 맥주·와인·하이볼의 가격으로 확장하지 않는다. 추정 금액을 DB의 실제 메뉴 가격으로 덮어쓰지 않는다.

### 4.3 자동 채우기와 산책

- 기본 순서는 필수 활동 확보 → 남은 시간과 예산에 맞는 유료 활동 → 예산 때문에 유료 활동을 추가하기 어려우면 무료 산책 검토다.
- **시간만 남는다고 산책을 넣지 않는다.** 유료 활동을 살 돈이 충분한데 공원을 의무적으로 끼우지 않는다.
- 산책은 실제 주변 후보와 이동·시간 조건이 맞아야 한다. 후보가 없으면 만들어 넣지 않는다.
- 유료 후보 자체가 없거나 가격을 모르는 상황을 ‘예산 부족’으로 추측해 산책으로 바꾸지 않는다.
- 자동 산책은 여러 개를 반복하지 않는다. 현재 구현은 직접 선택한 산책 또는 최대 1개 자동 산책을 고려한다.
- 산책을 직접 선택한 경우는 예산 부족 대체용 산책과 다르다. 예산 여유가 있어도 필수 활동으로 유지한다.
- `fillSchedule` ON일 때 놀거리·카페 검토는 기본 동작이다. 과거 `additionalActivities:["hotplace"]`가 남아서 유료 추가가 전부 차단되던 문제를 서버와 프론트에서 정규화했다. 이 옛 설정을 그대로 복원하지 않는다.
- `allowBudgetWalk`는 예산 부족 시 무료 산책 허용 여부다.

### 4.4 카페·놀거리·다양성

- 카페 기본 체류시간은 2시간이다.
- 사용자는 밤 8~9시 이후 친구 모임에 카페를 강제로 넣는 것을 원하지 않았다. 현재 구현은 동행과 무관하게 **20시 이후 자동 카페 도착을 제한**한다. 직접 선택한 카페는 별도다.
- 자동 카페가 저녁 식사 시간을 밀어내면 안 된다.
- 혼자일 때 보드게임카페는 추천하지 않는다.
- 선택한 놀거리 소주제를 자동 채움으로 계속 반복하지 않는다. 식사·카페도 자동 추가의 경험 다양성을 고려한다.
- 요청하지 않은 도자기 공방 등 만들기 체험을 일반 놀거리의 대표 대안으로 무조건 추천하지 않는다. 공방·만들기를 직접 선택한 경우는 허용한다.
- 장소 이름만 바꾸고 경험이 같은 코스를 3개 만드는 방식은 피한다. 후보 단계와 코스 비교 단계에서 다양성을 확보한다.

### 4.5 점심 이후 저녁 식사

- 낮 식사부터 저녁·밤까지 이어지는 일정에는 **18~20시 저녁 식사·반주를 다른 자동 여가보다 우선 확보**한다.
- 실제 이동 후 도착 시각으로도 저녁 시간대를 검증한다. 19:44 카페를 넣고 저녁 식사를 빠뜨리던 문제가 수정됐다.
- 점심과 같은 대표 메뉴를 반복하지 않는다. ‘한식 전체 제외’가 아니라 저장 메뉴·대표 음식 유형으로 비교하며, 식당의 찜닭과 포차의 찜닭도 같은 음식으로 본다.
- 식사 가능한 주점을 저녁 후보로 사용할 수 있다. 식사 메뉴 근거가 없는 술집을 자동으로 저녁 식사로 간주하지 않는다.
- 예산이 부족하면 자동 여가부터 줄인다. 저녁을 확보할 수 없으면 해당 사유를 안내한다.
- 저녁 식사 역할은 가게 교체 시에도 유지한다.

현재 코드의 적용 경계도 알아둘 것: 자동 채우기 ON, 선택한 food 슬롯의 예상 방문이 16시 전, 종료가 19시 이후이며 기존 필수 일정과 저녁 슬롯이 시간 안에 들어갈 때 예약한다. 모든 장기 여행의 아침·점심·저녁을 자동 보장하는 일반 식사 계획기는 아직 아니다. 식사를 고르지 않은 모든 장기 일정에 별도 식사 슬롯을 넣는 것으로 확대했다고 가정하지 않는다.

### 4.6 술집 2차·3차와 반주

- 술집을 선택했고 자동 채우기가 켜졌다면 서로 다른 술집을 연속으로 추천할 수 있다.
- 같은 포차 유형도 허용한다. 같은 가게를 다시 넣는 것은 금지한다.
- 2차·3차를 항상 추가하는 것이 아니라 남은 시간·예산·영업·도보 조건을 검증한다.
- 첫 번째로 선택한 술집 뒤에 추가 술집을 붙인다. 추가 술집을 필수 술집보다 앞에 놓지 않는다.
- 예: 18시 출발, 00:30 종료, 술집만 선택, 자동 채우기 ON이면 1차→2차→3차가 가능하다. 각 체류는 기본 약 2시간이며 실제 이동과 제약에 따라 줄어든다.
- **18~20시에 실제 도착하는 술집은 든든한 식사 메뉴가 있는 곳에 순위 가점**을 준다. 보쌈·족발, 고기, 전골·찌개, 식사 메뉴가 있는 이자카야 등이 의도에 맞는다.
- 가게 이름에 ‘포차’, ‘보쌈’이 들어가는지만 보지 않는다. 저장된 사용 가능한 메뉴, 제외 메뉴를 반영한 계산 메뉴를 근거로 한다.
- 이 반주 선호는 모든 일반 술집을 탈락시키는 필터가 아니다. 적합한 반주 후보가 없으면 유효한 일반 술집도 반환한다.
- 20시 이후 2·3차에는 저녁 식사 가점을 주지 않는다. 식사 메뉴를 계속 강요하지 않는다.

### 4.7 영업시간 — 최신 확정 사항

- **‘영업시간이 확인된 장소만 추천받기’ 체크박스를 제거했다.** PC에서도 공통 `AccuracyPreferences`를 사용하므로 다시 만들지 않는다.
- `plannerApi.ts`에서 항상 `allowUnverifiedHours:true`를 전송한다. 옛 브라우저 저장값 false도 덮어쓴다.
- DB와 외부 영업정보 확인은 계속 수행한다. ‘미확인 허용’은 영업시간 조회 자체를 끈다는 뜻이 아니다.
- 확인된 휴무·폐업·체류 중 영업 종료는 제외한다.
- 영업시간 미확인 후보는 추천에 포함할 수 있고, 방문 전 확인 안내와 카카오맵 연결을 제공한다.
- 구글에서도 시간 자료를 못 얻거나 매장 일치를 확신할 수 없는 경우가 있다. 모든 가게의 시간을 자동 확보했다고 말하지 않는다.
- 백엔드 API는 별도 요청의 `allowUnverifiedHours:false`를 아직 지원한다. 프론트 정책과 백엔드 지원 옵션을 혼동하지 않는다.

### 4.8 데이터·평점·링크

- 서울 전역에 수집한 DB를 활용한다. 건대 등 한 지역이나 특정 가게 몇 곳만을 위한 하드코딩으로 문제를 해결하지 않는다.
- 공유사무실·스터디카페, 공원 이름이 들어간 건설업체 등 실제 업종이 맞지 않는 후보는 추천에서 제외한다.
- ‘시우포차’는 사용자가 직접 추천 제외를 요청했던 장소다. 재수집이나 분류 변경으로 다시 살리지 않도록 기존 제외 처리를 확인한다. 이 문서 작성 시 운영 DB 전체를 재감사하지는 않았다.
- 포차는 이름 문자열이 아닌 업종·메뉴 경험으로 판단한다. 일식을 우동 몇 곳으로 축소하지 않는다.
- ‘맛집 탐방’, ‘가볍게 식사’, ‘대화’, ‘가성비’ 같은 포괄적 의도를 필수 태그 일치로 처리해 수백 후보가 전부 탈락하지 않게 한다. 구체적 업종·제외 메뉴와 구분한다.
- 해산물 제외는 매장에 해산물 메뉴가 하나라도 있으면 탈락시키는 의미가 아니다. 먹을 수 있는 다른 메뉴가 있으면 유지하고 그 메뉴로 비용을 계산한다.
- 간단 목록과 상세의 평점·리뷰 표시는 노플랜 DB 수집 정보를 사용한다. 외부 영업 조회 응답의 Google 평점으로 화면 값을 덮어쓰지 않는다.
- 산책 장소에는 별점·리뷰를 표시하지 않는다. 무료 산책이 가격 자료 부족으로 탈락하지 않게 한다.
- 평점 계산에서 공급자가 다른 평점과 리뷰 수를 한 쌍인 것처럼 섞지 않는다. 화면의 수집 정보와 내부 평점 신뢰도 계산은 구분한다.
- 장소 상세의 외부 지도는 네이버지도·카카오맵이 기준이다. 구글 평점 표시나 Google Maps 상세 링크를 다시 기본값으로 가져오지 않는다. 실제 경로 출처가 Google인 경우의 출처 문구는 별개다.
- 성별·나이대만으로 취향·지출을 단정하는 새 규칙을 만들지 않는다. 현재 대화에서 확정한 수단은 명시적 예산·동행·활동·취향 입력이다.

### 4.9 도보와 외부 API 비용

- 후보 조합·대략적 순서는 DB 좌표와 직선거리 기반 추정으로 비교한다.
- 실제 반환할 상위 코스부터 TMAP 보행자 경로를 확인한다. 실패하면 다음 후보로 넘어간다.
- 충분한 대안을 확보하면 중단하고, 공통 구간 캐시·진행 중 요청 공유를 활용한다. 비교 후보 전부에 TMAP을 먼저 호출하지 않는다.
- 일반 코스 대안은 최대 3개, 장소 교체 검증은 최대 6개다. 후보 부족 시 개수를 억지로 맞추지 않는다.
- ‘도보 짧게’ 선호, 검색 반경, ‘한 구간 최대 도보 거리’ 강제 제한을 서로 구분한다.
- 강제 거리 제한이 있을 때 추정 거리만 확인하고 실제 경로 검증이 끝났다고 표시하지 않는다.
- 사용자는 실제 TMAP 일일 한도 소진을 겪었다. 현재 계약 한도는 대시보드 확인 사항이며 문서의 과거 1,000회 언급을 영구 사양으로 취급하지 않는다.
- 429 한도/호출 제한은 ‘주변에 가게가 없음’과 다른 실패다. HTTP 200이어도 경로 본문이 유효한지 확인한다.

## 5. 문화·행사의 분리

- 코스 질문의 ‘하고 싶은 것’에는 문화·전시를 넣지 않는다. PC 구간 추천도 같은 정책이다.
- 행사 탐색 페이지는 유지하며, 사용자가 명시적으로 행사 상세에서 여행에 담는 것은 가능하다. 일반 추천에서 제외하는 것과 여행 담기를 막는 것은 다르다.
- 코스 결과 아래에 **실제 코스 장소의 방문 날짜와 위치**를 기준으로 주변 행사를 보여준다.
- 기존 구현 기준 각 장소 직선거리 1km 이내, 방문일과 개최 기간이 겹치는 행사 최대 3개다.
- 거리 표시는 직선거리이며 도보 경로로 가장하지 않는다. 관람 시간·예약 가능 여부까지 보장한 추천은 아니다.
- 행사 API 실패·일치 행사 없음은 코스 추천 실패로 전파하지 않는다.
- ‘전시’ 버튼을 누르면 결과 하단 전시 영역으로 이동하는 아이디어가 있었지만 **사용자가 아직 하지 말자고 보류했다.** 이번 PC 작업에서 확정 기능처럼 추가하지 않는다.

## 6. PC 작업에서 먼저 점검할 부분

아래는 현재 코드에서 보이는 점검 대상이다. 모두 새로 개발하기로 확정된 목록은 아니다.

1. **홈·탐색·내 여행의 PC 배치**: 기존 여행 생성 진입과 GNB를 유지하며 사용자가 지정한 화면부터 개선한다.
2. **여행 편집기의 추천 연결**: `TripRecommendations.tsx`는 공통 `generateCourse`와 `AccuracyPreferences`를 사용한다. 별도 추천 로직을 만들지 않는다.
3. **추천 대안 비교**: 공통 추천 화면에는 여러 코스 비교가 있으나, PC 구간 추천은 현재 첫 결과의 장소를 미리보기로 담는 흐름이다. 동일한 비교 UI가 이미 모두 연결됐다고 가정하지 않는다.
4. **예산 범위**: PC 구간 추천 입력은 ‘이번에 추가할 일정의 1인 예산’이다. 여행 전체 예산·이미 쓴 금액을 자동 차감하는 기능으로 오해하지 않게 한다.
5. **시간·메타데이터 보존**: `tripModel.ts`의 `toTripPlace`와 저장 검증을 확인한다. 추천 장소를 여행 모델로 바꾸면서 `mealRole`, 정확한 방문 시각, 이동·가격 근거가 모두 유지된다고 가정하지 않는다.
6. **구간 연결의 한계**: 편집기는 이동 여유를 보수적으로 계산하지만 다음 구간 목적지까지의 전체 경로 최적화를 보장하지 않는다. 현재 `TripRecommendations.tsx`에는 최소 15분 이동 여유와 구간 종료 검사가 있다.
7. **지원 지역 판별**: PC 구간 추천의 `supported`는 현재 지역명 문자열과 도보 여부를 사용한다. 일부 서울 지역명이 빠질 수 있는 점검 대상이며, 서울 전체 지원을 특정 역 목록으로 축소하지 않도록 확인한다.
8. **정확한 진행 상태**: 서버 진행 이벤트를 사용해 체크 단계가 갱신되는 기능을 유지한다. 단순한 가짜 타이머나 영구 로딩으로 되돌리지 않는다.
9. **교체와 저장**: 저녁 반주 술집과 늦은 술자리, 첫 술집과 2차를 구분해 교체해야 한다. 나머지 가게·전체 시간·예산을 유지하고 실제 사용자 적용 전 저장하지 않는다.

## 8. 검증 상태와 앞으로의 검증 기준

### 이 대화에서 마지막으로 완료한 검증

- 공통 백엔드 전체 테스트 **496개 통과**: 반주 우선, 저녁·일반 술집 역할을 유지한 교체, 짧은 오후 일정, 2·3차 연속 방문 등을 포함한다.
- 영업시간 체크박스 제거 및 옛 false 값 무시 변경 후 프론트 `npm run build` 통과.
- 프론트에는 기존 500kB 초과 번들 경고가 남아 있다. 빌드 실패와 구분한다.
- 일부 청량리 실제 DB 장소·메뉴로 읽기 전용 재현을 했다. 그 재현은 실시간 Google 영업 조회·TMAP 호출을 생략했으므로 운영 방문 가능성까지 검증한 결과로 확대 해석하지 않는다.
- 이 문서 작성은 코드 읽기와 문서 정리 작업이며 테스트 전체를 다시 실행하거나 운영 서버를 배포하지 않았다.

### PC 변경 후 확인할 대표 시나리오

| 시나리오 | 유지할 결과 |
|---|---|
| 14:28~00:30, 3명, 7만원, 식사·카페·술집 | 필수 활동 + 점심과 다른 저녁 메뉴, 저녁 18~20시 우선, 남은 시간 채움 |
| 18:00~00:30, 술집만 선택 | 시간·예산이 되면 서로 다른 술집 연속, 저녁 반주 우선 |
| 20시 이후 추가 술집 | 식사 메뉴 가점 강요 없음, 일반 2·3차 가능 |
| 예산 충분 + 시간 남음 | 산책부터 끼우지 않고 유료 활동 검토 |
| 예산 부족 + 시간 남음 | 실제 주변 무료 산책 가능 여부 검토, 무조건 생성 금지 |
| 6시간과 7시간 | 특정 시간값 전용 로직 없이 실제 남은 시간 계산 |
| 혼자 + 놀거리 | 보드게임카페 제외 |
| 해산물 제외 + 비해산물 메뉴 있음 | 먹을 수 있는 메뉴가 있으면 매장 유지·그 메뉴로 계산 |
| 가격 범위 최대값만 예산 초과 | 평균이 예산 내면 후보 가능, 범위·주의 표시 |
| 옛 저장 조건에 영업 미확인 허용 false | PC·모바일 요청은 true 전송, 별도 체크 UI 없음 |
| 영업 미확인 / 휴무 확인 | 전자는 안내 후 포함 가능, 후자는 제외 |
| 술집·저녁 장소 교체 | 고정한 나머지 가게·필수 활동·예산·시간 유지 |
| TMAP 429 / 경로 본문 오류 | 가게 없음과 구분, 요청 폭증 방지 |
| PC 폭 변경 / 추천 중 리사이즈 | 입력·초안·진행 상태 유지 |
| 여행 구간 수정 후 이전 추천 적용 | 오래된 결과 적용 차단 |
| 행사 없음 / 행사 조회 오류 | 코스 추천 결과는 정상 유지 |

추천 로직을 수정할 경우 새 회귀 테스트는 실제 요청 경로와 연결한다. 내부 함수 한 개만 통과한 것으로 프론트→요청 정규화→추천→결과→교체까지 확인했다고 보고하지 않는다. UI만 바뀌면 필요한 빌드·화면 검증에 집중한다.

실행 명령:

```powershell
# 프론트 저장소에서
npm run build

# 백엔드 저장소에서
npm test
```

EC2 로그 확인 예시:

```bash
pm2 logs noplan-backend --lines 200 --nostream
```

같은 `requestId`의 `[course-request]`, `preferences-normalized`, `time-window-resolved`, 후보 수·필터 통계, `scheduleAttempts`, `walking-route-diagnostics`, `[course-result]`를 묶어서 본다. 서로 다른 요청의 stdout·error 로그를 한 실행으로 섞지 않는다.

## 9. 보류·미확정 범위

- 친구 초대·권한·실시간 공동 편집은 핵심 기능 이후로 연기됐다. 초기 PC 기획서에 상세하게 적혀 있어도 현재 구현 범위로 자동 채택하지 않는다.
- 협업 변경 이력과 기존 개인 초안·되돌리기·버전 충돌 보호는 다르다. 이미 있는 개인 보호 기능은 유지한다.
- 전국 AI 추천, 자동차·대중교통 경로 최적화, 항공·숙박 예약·결제는 현재 지원 완료로 표시하지 않는다.
- PC 구간 사이의 다음 예약 장소까지 포함한 전체 여행 경로 최적화는 별도 작업이다.
- 로그인 후 불필요한 정보 자동 입력은 방향성이다. 현재 저장되는 기본 취향과 매번 받아야 하는 인원을 확인한 뒤 확장한다.
- 전시 영역으로 이동하는 전용 버튼은 보류 상태다.
- 향후 PC 화면의 구체적 개편 범위는 새 작업에서 사용자 요청을 따른다. 이 문서의 점검 목록을 일괄 구현하지 않는다.
