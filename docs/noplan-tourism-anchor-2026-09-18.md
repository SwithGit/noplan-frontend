# PC 중심 관광지 일정 추가 — 2026-09-18

## 사용 흐름

1. PC 홈에서 목적지와 여행 날짜를 입력한다.
2. `관광지부터 고르기`에서 관광지 이름 또는 지역명을 검색한다. 예: `첨성대`, `태화강`.
3. 결과의 주소를 확인하고 관광지와 예상 관람시간을 선택한다.
4. 홈에서 방문 날짜와 오전·오후·저녁 구간을 고른 뒤 `여행 만들기`를 누른다.
5. 선택한 구간에 중심 관광지가 첫 번째 고정 장소로 들어간다. 다른 구간에서도 `중심 관광지 담기`로 추가할 수 있다.
6. 해당 구간의 `이 구간 추천받기`는 관광지 관람 후 남은 시간과 마지막 장소 좌표를 기존 도보 코스 알고리즘에 전달한다. 기존 소주제 장소가 있으면 그 마지막 장소부터 이어 붙인다.

관광지·관람시간 변경, 중심 관광지 제거, 되돌리기, 브라우저 초안 보관 및 로그인 계정 저장을 지원한다. 관광지를 교체할 때 기존 소주제 장소를 지우지 않는다. 이동과 운영시간은 사용자가 다시 확인해야 한다.

## 데이터와 구현

- `GET /api/tourism/search?keyword=첨성대&type=12&page=1`
- 서버의 기존 `PUBLIC_DATA_SERVICE_KEY`로 한국관광공사 `KorService2/searchKeyword2` 조회. 키를 브라우저로 보내지 않는다.
- 관광지(12), 문화시설(14), 레포츠(28)를 선택해서 검색. 전국 키워드 검색이며 주소 기반 도시 필터나 인기순 순위는 아니다. 한국관광100선 인증 표시는 하지 않는다.
- 한 페이지 20건, 최대 5페이지. 좌표 없는 항목·유형이 다른 항목 제외. 오류와 빈 결과 구분.
- 검색 캐시 10분·최대 150개, 동일 요청 병합, 외부 요청 동시 20개 제한, 요청 제한 분당 30회, 제공기관 타임아웃 12초.
- 관광지 원본 전체를 카탈로그 DB에 적재하지 않는다. 선택한 이름·주소·좌표·관람시간·TourAPI ID를 여행 문서에 보존한다. 기존 여행 저장 테이블을 쓰므로 추가 DB 스키마 변경이 없다.
- `TripPlace.source = tourism`, `tourism = {contentId, contentTypeId}`, `fixed = true`, `priceNeedsCheck = true`.
- 한 구간의 중심 관광지는 한 곳이며 첫 장소로 유지한다. 동일 날짜 다른 구간의 동일 관광지 추가, 장소 수 초과, 관람시간+기존 장소+이동 여유의 구간 초과를 추가/변경 시 차단한다.
- 관광지 입장료와 운영시간을 조회·검증한 것으로 표시하지 않는다. 관람시간 기본값은 사용자 조정용이며 제공기관의 권장시간이 아니다.
- 기존 DB 우선 → DB 후보가 없으면 Kakao 실시간 검색 → 공통 코스 생성 흐름을 그대로 사용한다. 이번 기능은 사용자가 중심 관광지를 선택하는 단계이며 여러 관광지의 자동 배분·차량 동선 최적화는 포함하지 않는다.

## 배포

백엔드 관광지 라우트와 여행 저장 검증 변경을 먼저 반영하고 프론트엔드를 배포한다. 프론트만 배포하면 관광지 검색/계정 저장이 지원되지 않는다. 이 작업에서는 로컬 구현·검증만 했으며 운영 서버를 배포하거나 운영 DB에 쓰지 않았다.

## 검증

- 프론트 Node 테스트 9개 통과, TypeScript/Vite 빌드 통과. 기존 500KB 초과 번들 경고는 남아 있다.
- 백엔드 전체 테스트 513개 통과. 공식 검색 정규화/캐시/오류/HTTP 쿼리 검증 및 여행 저장·재조회에서 관광지 정보 보존 확인.
- 기존 실제 키로 `첨성대` 1건, `태화강` 5건(태화강 국가정원 포함), `경주` 첫 페이지 20건 및 다음 페이지 여부 확인.
- 브라우저에서 실제 첨성대 검색 → 오후 구간에 담기 → 관광지와 주소 표시 → 90분에서 60분 변경 시 추천 시작 14:45에서 14:15로 변경 확인.
- 새로고침 보존, 300분 입력 시 구간 초과 차단, 중심 관광지 제거와 되돌리기 확인.
- 다른 날짜/구간의 독립성은 모델 테스트로 확인. 내장 테스트 브라우저의 기본 달력 팝업이 종료되어 다일 여행의 달력 클릭 검증은 완료하지 못했다.
- 이번 화면 검증은 실제 TourAPI를 연결한 임시 로컬 API로 진행했다. 운영 계정/DB 및 Google·TMAP을 포함한 소주제 코스 생성 전체 실연은 별도 확인이 필요하다.

공식 API 안내: https://www.data.go.kr/data/15101578/openapi.do

## PC 관광지 선택 UX 개선 (2026-09-18)

- 기존 520px 세로 모달을 최대 1320px 데스크톱 선택 화면으로 교체했다.
- 왼쪽은 큰 사진이 있는 2열 카드 목록, 오른쪽은 선택한 장소 상세와 관람시간/담기 버튼이다. 짧은 노트북 화면에서도 관람시간과 최종 버튼을 고정 노출한다.
- 첫 진입에는 목적지, 수정 시에는 기존 관광지 이름으로 자동 검색한다. 종류는 드롭다운 대신 바로 누르는 필터 버튼을 사용한다.
- 1시간/1시간 30분/2시간 빠른 선택, 검색 로딩·빈 결과·실패 재시도, 사진 미제공/실패 대체 화면을 추가했다.
- TourAPI firstimage/firstimage2와 cpyrhtDivCd를 API 응답에 포함한다. 사진 출처를 표시하고 Type3 사진은 자르지 않고 전체 비율로 보여준다. 사진 URL은 관광공사 공식 호스트만 허용하고 HTTPS로 정규화한다.
- 여행에 저장하는 관광지 구조는 유지한다. 수정 화면의 사진은 공식 검색으로 다시 불러온다.
- 실제 울산 사진 카드, 선택 강조, 60분 빠른 선택과 홈 반영, 다시 열기 및 1024px/1280px PC 레이아웃을 브라우저에서 확인했다.
- 빌드·변경 파일 ESLint·관광지 모델 테스트 3개·백엔드 관광지 API 테스트 4개 통과. 모바일 코스 추천 오류는 요청대로 후속 작업으로 남겼다.
- 사진 응답 변경을 사용하려면 백엔드 재시작/배포도 필요하다. 운영 배포는 수행하지 않았다.

## 주변 코스 실패 수정·이동수단 연결 (2026-09-18)

- `candidateCount:0` 재현: 전달받은 울산 좌표에서 전체 주소 + `카페 디저트` 검색은 0건, 좌표/반경 + `카페` 검색은 첫 페이지 15건이었다. 실시간 검색에서는 위치 접두어를 제거하고 일반 카페 검색어를 단순화한다. 구체적인 활동·음식 취향 검색은 유지한다.
- PC 현지 이동 선택을 `generate-course.transportMode` (`walk`/`car`, 기본 `walk`)로 전달한다. 도보는 반경 1.5km, 자가용·렌터카는 10km. DB 조회와 실시간 검색, 최종 후보 거리 필터에 동일하게 적용한다. 대중교통 자동 추천은 지원하지 않는다.
- 차량은 카카오 모빌리티 자동차 길찾기 응답으로 이동시간을 확인하고 장소마다 주차 여유 5분을 추가한다. 현재 교통 기준이며 방문일 교통/주차 가능 여부를 보장하지 않는다. 유류비·통행료·주차비는 기존 활동 예산에서 제외됨을 안내한다. 경로 확인 실패를 도보 추정 시간으로 통과시키지 않는다.
- 인증은 `KAKAO_MOBILITY_REST_API_KEY`가 있으면 사용하고, 없으면 기존 `KAKAO_REST_API_KEY`를 사용한다. 로컬 키로 실제 자동차 경로 조회 성공을 확인했다. 별도 DB 스키마 변경은 없다.
- 공통 엔진의 요청·자동 추가 카페 최소 체류를 30분으로 맞추고, 여유가 있으면 기존 선호 체류 120분을 유지한다. 30분 경계 및 75분 구간을 회귀 테스트한다.
- PC는 추천 요청 전후에 15분을 중복 추가하지 않는다. 서버의 `scheduledStart`/`scheduledEnd`에서 이동·대기 시간을 한 번 계산하여 `TripPlace.travelMinutes`에 보관하고, 저장/재조회 및 다음 추천의 출발시간에 반영한다. 직접 편집으로 앞 장소/순서/시간/이동수단이 바뀌면 저장된 이동시간을 초기화하여 기존 15분 임시 계산을 사용한다.
- DB 우선, DB 후보가 없을 때만 실시간 검색, 실시간 가게 원본 미적재, 가격 확인 필요·총예산 미검증 안내는 유지한다. `candidates-ready` 로그에 이동수단·반경·DB/실시간 후보 수·실시간 검색 여부를 추가했다.
- 검증: 백엔드 전체 522개, 프론트 모델/스트림 12개 통과. 변경 파일 ESLint 및 TypeScript/Vite 빌드 통과. 전체 프론트 lint에는 기존 `dev-preview/course-cards.tsx`, `MapBoard.tsx`의 오류 10개가 남아 있으며 기존 번들 크기 경고도 유지된다.
- 운영 배포는 수행하지 않았다. 백엔드 변경/재시작 후 프론트 빌드를 반영해야 한다. 운영 DB를 통한 로그인 추천 전체 흐름은 이번 테스트 범위에 포함하지 않았다.
