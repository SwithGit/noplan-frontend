# PC 여행 조건 및 관광지 연결 API

## 반영 내용

- 홈과 새 여행 만들기에 반려동물 종류, 체중, 실내 동반 필요 여부를 추가했다.
- 출입구, 장애인 화장실·주차구역, 엘리베이터, 유모차 대여, 수유실을 `선택 안 함 / 있으면 좋아요 / 꼭 필요해요`로 선택한다.
- 조건은 브라우저 초안과 계정 여행 JSON에 저장한다. 코스플래너 공통 조건 및 여행 정보에서 변경할 수 있다. 이미 만든 일정은 자동 삭제하거나 교체하지 않는다.
- 자동 추천은 반려동물 조건과 필수 시설이 확인된 장소만 사용한다. 선호 시설은 가점으로 반영한다. 정보 없음, 조건부 시설, 조회 실패를 시설 보유로 추정하지 않는다.
- 조건을 만족하는 가까운 장소가 부족하면 두 장소의 짧은 코스를 시도하고 안내한다. 실제 이동거리 검증과 도보 1km·차량 7km 제한, 백화점 자동 제외는 유지한다.
- 장소 선택·교체 화면에 현재 페이지의 조건 필터, 상세 안내, 연관 관광지 목록을 추가했다. 직접 검색·등록은 허용하며 확인되지 않은 조건은 방문 전 확인하도록 표시한다.
- 홈에 기초지자체 중심 관광지 선택을 추가했다. 중심 순위와 연관 순위는 자동 추천의 소폭 가점에 사용한다. 거리 제한보다 우선하지 않는다.
- 새 UI 문구는 한국어·영어·중국어 간체·일본어로 제공한다. 공식 자유서술 안내는 `한국어 원문`으로 명시한다. 이 문장을 번역해 시설 보유 여부를 추론하지 않는다.

## 사용하는 API

| 기능 | 서비스 / 오퍼레이션 |
| --- | --- |
| 반려동물 | `KorPetTourService2/areaBasedList2`, `detailPetTour2` |
| 무장애 시설 | `KorWithService2/areaBasedList2`, `detailWithTour2` |
| 기초지자체 중심 관광지 | `LocgoHubTarService1/areaBasedList1` |
| 관광지별 연관 관광지 | `TarRlteTarService1/searchKeyword1` |
| 법정동 코드 | 기존 `KorService2/ldongCode2` |

네 신규 서비스 모두 기존 키로 HTTP 200 / resultCode 0000을 확인했다. 실제 상세 응답과 노원구 중심 관광지 매칭도 확인했다.

중심·연관 데이터의 관광지 ID와 TourAPI `contentid`는 다른 체계다. 이름 정규화와 좌표 150m 이내 일치가 유일한 장소에만 중심 ID를 연결한다. 연관 장소는 그 연결이 확인된 ID만 사용한다. 연결하지 못한 장소는 임의로 다른 장소에 붙이지 않는다.

## 배포

**프론트와 백엔드 모두 배포해야 한다. 백엔드를 먼저 반영한다.**

백엔드 `D:/Backend/NoPlan` 변경:

- `routes/tourism/travelSupport.js`, `travelSupportRouter.js`
- `routes/tourism/router.js`
- `routes/trips/validation.js`
- `middleware/pcDiagnostics.js`
- `.env.example`, 관련 테스트

기존 `PUBLIC_DATA_SERVICE_KEY`를 그대로 사용한다. 새 API 키를 프론트 환경변수에 추가하지 않는다. 기존 여행 JSON에 선택 필드를 추가했으므로 DB 테이블 변경은 필요 없다.

선택 환경변수 `TOURISM_CONNECTION_BASE_YM=202504`: 공식 문서의 제공 범위 안에서 실제 응답을 확인한 기준월이다. 여행 날짜나 현재 월과 다르다. 화면에도 기준월을 표시한다. 더 최근 데이터가 제공되는 것을 확인한 뒤 변경하고 백엔드를 재시작하면 된다.

새 엔드포인트:

- `GET /api/tourism/travel-support/places?ids=...` — 최대 20개 장소
- `GET /api/tourism/travel-support/catalog?destination=...&pet=1&access=1&requiredAccess=1` — 추천 후보의 조건 정보
- `GET /api/tourism/travel-support/discovery?destination=...&anchorId=...` — anchorId 생략 시 중심 관광지, 지정 시 연관 관광지

EC2에는 `[pc-request]`, `[pc-result]`, `[pc-provider]`로 조회·부분 실패·공급자 실패가 남는다. 체중이나 개별 편의시설 선택값은 진단 로그에 남기지 않는다.

## 운영상 범위

- 시설 정보는 개별 장소의 정보다. 장소 사이 경사·계단·휠체어 통행 가능 경로를 보장하지 않는다.
- 반려동물 종류가 비어 있거나 크기 제한을 판별할 수 없으면 자동 추천에서 제외될 수 있다. `전구역 동반가능`만으로 동물 종류나 실내 허용을 추론하지 않는다. 목줄·이동장 등 조건은 상세 원문을 함께 보여준다.
- 추천 후보는 구·유형별로 나눠 최대 120곳의 상세를 확인한다. 상세 확인은 40초 이후 새 호출을 시작하지 않는다. 미확인 후보나 API 실패가 있으면 부분 조회로 명시한다. 지역 전체에 적합한 장소가 없다고 단정하지 않는다.
- 지역 목록은 API당 최대 5,000개를 조회한다. 큰 시·도 중심 관광지는 최대 6개 기초지자체를 먼저 확인하며 부분 범위를 안내한다. 연관 장소는 현재 선택 지역 안에서 식별된 장소로 제한한다.
- 공급자 성공 응답은 프로세스 메모리에 24시간, 최대 3,000건 캐시한다. 재시작하면 초기화된다. 동일 요청을 합치고 403/429에는 1분간 재호출을 억제한다. 여러 EC2 프로세스는 캐시를 공유하지 않는다.
- 공식 상세 조회는 자동 추천 때 확인하지 않은 나머지 출처도 별도로 조회한다. 자료 변경이나 부분 실패가 있으면 기존 추천 장소라도 확인 필요로 표시될 수 있다.

## 검증

- 백엔드: 조건 필드 저장·검증, 원문 판정, 이름·좌표 매칭, API 캐시·부분 실패, HTTP 입력 검증, 로그 민감 필드 제외.
- 프론트: 필수/선호 구분, 체중 경계와 실내 정보 없음, 짧은 코스에도 실제 거리 제한 유지, 백화점 제외 및 기존 다일 일정 회귀, 초안 재조회, 새 문구 3개 외국어 번역 검사.
- UI 검증은 사용자 진행. 개발 중 사용한 임시 API는 결정적 테스트 응답을 사용했으며 실제 경로·시설 보장을 위한 증거로 사용하지 않는다.

직접 확인할 흐름: 홈에서 조건 선택 → 여행 생성 → 노피 공통 조건 유지 → 자동 코스 → 상세·장소 변경 → 직접 추가 → 일정 반영 후 새로고침. 지역 중심 관광지와 선택한 장소의 연관 관광지도 펼쳐 확인한다.
