## 1. 기획에 전달할 핵심 결론

기존 공공데이터 연동은 장소 존재·주소·영업상태 검증에는 유효했지만, Redtable에 없는 장소의 메뉴를 확보할 수 없었다.

이번 개발에서는 이미 카카오 수집과 네이버 존재 확인을 통과해 검수함에 저장된 후보만 네이버 플레이스 상세정보로 다시 조회하도록 별도 메뉴 수집 흐름을 추가했다.

실제 성수 대기 후보 69곳에 적용한 결과는 다음과 같다.

|---|---:|

이전 문서에서 `현재 데이터 소스만으로는 다수 장소의 메뉴 자동 확보가 어렵다`고 판단했던 문제는 이번 네이버 상세 메뉴 수집으로 해소됐다. 단, 네이버 공식 API가 아니라 Apify의 커뮤니티 Actor를 사용하는 방식이므로 이용약관·수집 정책·비용 정책은 운영 전에 별도로 확인해야 한다.

## 3. 최종 데이터 흐름

```text
Apify 카카오 후보 수집
→ 기존 네이버 검색 결과로 장소 존재 교차검증
→ 검수 후보 DB 저장
→ 저장된 후보만 네이버 상세정보 재조회
→ 네이버 장소 ID·주소·전화·좌표로 장소 일치 검증
→ MenuItems 메뉴명·가격 정규화
→ 기존 수동·Redtable 메뉴와 병합
→ 관리자 검수
→ 추천 장소 승인 시 출처 정보와 함께 승인 메뉴로 복사
```

기존 후보 수집 단계의 네이버 설정은 성능과 비용 보호를 위해 그대로 유지했다.

```text
scrapePlaceDetails: false
```

후보로 저장된 장소의 메뉴를 가져오는 별도 요청에만 다음 설정을 사용한다.

```text
scrapePlaceDetails: true
maxResultsPerKeyword: 5
```

## 4. 관리자 화면 사용 방법

### 후보 한 곳 메뉴 수집

1. 관리자 장소 화면에서 `성수역`을 선택한다.
2. 검수함에서 후보를 선택한다.
3. 상세 화면 상단의 `네이버 메뉴 불러오기`를 누른다.
4. 메뉴가 발견되면 메뉴명·가격·출처·신뢰도·최근 확인일이 표시된다.

이미 확인한 후보에는 버튼이 `네이버 메뉴 다시 확인`으로 바뀐다. 이 버튼은 확인창을 거쳐 24시간 캐시를 무시하고 새로 조회한다.

### 여러 후보 일괄 수집

1. 성수 검수함에서 후보 왼쪽 체크박스를 선택한다.
2. 현재 페이지 전체가 필요하면 `현재 페이지 전체`를 선택한다.
3. `선택한 후보 메뉴 일괄 수집`을 누른다.
4. 완료 후 다음 수치가 관리자 알림에 표시된다.

```text
전체 처리 장소
메뉴 확인 장소
반영 메뉴 수
메뉴 없음
미확인 또는 검수 필요
오류
```

일괄 API는 한 번에 최대 100개를 받고 내부적으로 15개 단위로 처리한다. 한 후보가 실패해도 나머지 후보는 계속 처리한다.

## 5. 장소 매칭 안전 기준

다른 지점의 메뉴가 붙는 문제를 막기 위해 상호명만으로 자동 저장하지 않는다.

자동 매칭 우선순위:

1. 기존 네이버 장소 ID 완전일치
2. 기존 네이버 장소 URL 완전일치
3. 전화번호 완전일치와 호환되는 상호명
4. 상호명 완전일치와 도로명주소 일치
5. 상호명 완전일치와 좌표 100m 이내

동명이거나 지점이 불명확하면 메뉴를 저장하지 않고 `review_required`로 끝낸다.

프랜차이즈는 지점명·주소·전화번호 중 확실한 근거가 없으면 자동 매칭하지 않는다.

## 6. 메뉴 정규화 규칙

허용하는 메뉴 배열 필드:

```text
MenuItems
menuItems
menus
menu
```

허용하는 메뉴명 필드:

```text
Name
name
title
MenuName
menuName
```

허용하는 가격 필드:

```text
Price
price
priceText
amount
```

가격 처리:

- `4,500원`, `4500`, `₩4,500` → 숫자 `4500`
- `변동`, `시가`, `가격 문의` → `price=NULL`, 원문은 `price_text`
- 0원·음수·비정상 가격 → 정상 숫자 가격으로 취급하지 않음
- 메뉴명이 없는 항목 → 저장하지 않음
- 같은 장소에서 메뉴명·가격이 같은 항목 → 한 건만 저장
- 메뉴 이미지 → 이번 범위에서는 저장·게시하지 않음

네이버가 안정적인 메뉴 ID를 제공하지 않는 경우 다음 값을 SHA-256으로 해시해 `source_menu_id`로 사용한다.

```text
네이버 장소 ID + 정규화 메뉴명 + 숫자 가격 또는 가격 원문
```

## 7. 기존 메뉴 보호와 우선순위

메뉴 출처 우선순위:

```text
수동 입력·팀 업로드·점주 입력
> 네이버 플레이스
> Redtable
```

적용 규칙:

- 수동·팀·점주 메뉴는 자동수집이 덮어쓰지 않는다.
- 같은 메뉴가 네이버와 Redtable에 모두 있으면 네이버 메뉴 하나만 노출한다.
- 네이버에 없는 Redtable 메뉴는 유지한다.
- 자동 메뉴를 수정하면 `manual` 출처로 전환한다.
- 수정하면서 기존 `source_place_id`, `source_menu_id`는 추적용으로 유지한다.
- 자동 메뉴를 삭제하면 행을 물리적으로 지우지 않고 `is_available=0`으로 비활성화한다.
- 비활성화한 자동 메뉴는 재수집해도 다시 노출하지 않는다.
- 승인 시 활성 메뉴만 `noplan_place_menu_items`로 복사한다.

## 11. 관리자 상세 빈 화면 장애와 수정

### 증상

성수역 검수함에서 후보를 누르면 목록은 남아 있지만 오른쪽 상세 화면 전체가 비어 보였다.

### 원인

MySQL `DECIMAL` 타입인 `match_confidence`가 Node.js에서 문자열 `"1.000"`으로 반환됐다. 프론트 출처 표시가 이 값을 숫자로 가정하고 `toFixed(2)`를 직접 호출하면서 React 렌더링 예외가 발생했다.

### 수정

- Frontend가 숫자와 문자열을 모두 안전하게 `Number()`로 변환한 뒤 표시
- 유효한 숫자가 아니면 `-` 표시
- Backend 후보 상세 응답에서도 `matchConfidence`를 숫자로 정규화
- `isSignature`, `isAvailable`도 Boolean으로 정규화
- 관리자 화면의 다른 `toFixed()` 사용 위치를 함께 점검

### 데이터 영향

렌더링 문제였으며 DB 메뉴 데이터 손실은 없었다. 수정 후 성수 후보 상세와 메뉴가 정상 표시되는 것을 확인했다.

## 13. Apify 사용량과 비용 참고

사용 Actor:

```text
delicious_zebu~naver-map-search-results-scraper
```

Actor 페이지에 표시된 가격은 현재 `1,000 results당 $1.50부터`다.

이번 최초 보강은 69개 장소 결과를 사용했으므로 결과당 요금만 단순 계산하면 약 `$0.10`이다.

```text
69 / 1000 × $1.50 = $0.1035
```

이 값은 단순 추정치다. 실제 청구액은 Apify 요금제, Actor 정책, 실행 컴퓨팅 비용과 최소 과금 여부에 따라 달라질 수 있으므로 Apify 콘솔 사용량을 최종 기준으로 확인해야 한다.

Actor 정보:

https://apify.com/delicious_zebu/naver-map-search-results-scraper

## 14. 배포 범위

Frontend와 Backend를 모두 배포해야 한다.

### Frontend

- 단건·일괄 메뉴 수집 버튼
- 후보 선택 체크박스
- 출처·신뢰도·최근 확인일
- 숫자·문자열 신뢰도 안전 처리

### Backend

- 신규 메뉴 API
- 네이버 메뉴 Provider와 병합 서비스
- 공통 Apify 실행기
- 메뉴 삭제 억제와 출처 우선순위
- 후보 상세 응답 타입 정규화

### 환경변수

새 환경변수는 없다.

```text
APIFY_API_TOKEN
```

기존 값을 그대로 사용한다.

### MySQL

추가 SQL은 없다. 기존 스키마를 사용하며 실데이터 1,248개는 이미 연결 DB에 저장됐다.

### Backend 재시작

배포 후 PM2 Backend 프로세스를 재시작해야 한다.
