# 친구와 공동 일정 편집

## 사용 흐름

1. 일정 화면 오른쪽 위 **친구와 함께**를 누른다. 계정에 저장하지 않은 일정은 먼저 저장한다.
2. 여행을 만든 사람이 초대 링크를 생성하고 복사한다. 링크는 7일간 유효하다.
3. 친구가 링크를 열고 로그인한 뒤 **함께 편집하기**를 누른다. 로그인/소셜 가입 뒤에는 초대 화면으로 돌아온다.
4. 같은 여행이 두 사람의 ‘내 여행’에 표시된다. 장소·구간·관광지·관람시간·순서·메모·여행 정보를 기존 편집 화면에서 바꾼다.
5. 공동 여행은 변경을 800ms 모아 자동 저장한다. 상대방의 열린 화면은 3초 간격으로 갱신한다. 정상 연결에서는 저장 후 수초 내 반영된다.

여행을 만든 사람만 초대 링크 생성/만료와 참여자 제외를 할 수 있다. 참여자는 모두 편집자다. 최대 20명이며 링크만 보고 있는 사람에게는 일정 내용을 공개하지 않는다. 링크 생성은 초대 메시지를 자동 전송하지 않는다.

## 동시에 수정할 때

- 서버는 저장 버전을 비교해 오래된 버전의 PUT을 409로 거절한다.
- 프론트는 마지막 저장본·내 작업본·최신 서버본을 비교해 서로 다른 항목의 수정과 추가를 합친다. 장소와 구간은 배열 위치가 아닌 고유 ID로 연결한다.
- 같은 필드에 서로 다른 값을 입력하거나, 삭제와 편집이 충돌하거나, 순서 변경이 서로 모순되면 자동 저장을 멈춘다. 현재 작업본을 유지하고 ‘최신 여행 열기 / 새 여행으로 복사’를 안내한다.
- 충돌한 작업본을 이어서 편집하거나 새로고침해도 원래 기준 버전이 보존된다.
- 병합 결과도 기존 서버 검증(시간 겹침, 장소 수, 중심 관광지 수 등)을 통과해야 저장된다. 검증 실패는 작성본을 보존하고 오류를 안내한다.
- 편집 대화상자가 열린 동안에는 원격 내용으로 폼의 바탕을 바꾸지 않는다. 대화상자를 닫은 다음 병합한다. 원격 수정 반영 시 예전 ‘되돌리기’ 기록은 초기화해 친구 수정을 과거 전체 문서로 되돌리는 것을 방지한다.
- 권한이 회수되거나 로그인이 만료되면 서버 저장을 차단하고 로그인/최신 여행 열기/새 여행으로 복사 경로를 표시한다.
- 네트워크 저장 실패 시 작업본을 브라우저에 남긴다. 오류를 확인하고 ‘여행 저장’으로 재시도할 수 있다. 저장 완료 전 창을 닫을 때 경고한다.
- 문자를 타이핑하는 중인 커서나 다른 사람의 온라인 상태까지 공유하는 기능은 이번 범위에 포함하지 않았다.

## 권한·저장 구조

기존 `noplan_trips`를 유지하고 `noplan_trip_members`, `noplan_trip_invites` 두 테이블을 추가한다. API의 읽기·목록·수정은 로그인된 소유자 또는 참여자만 허용한다. 요청 본문에서 보낸 사용자 ID는 사용하지 않는다. 새 참여자는 서명된 로그인 세션과 유효한 초대 토큰을 모두 가져야 한다.

초대 토큰은 32바이트 난수이고 DB에는 SHA-256 해시만 저장한다. 링크에서는 URL fragment를 사용해 일반 요청 경로·Referrer에 토큰을 넣지 않는다. 새 링크를 만들거나 링크를 만료시키면 기존 링크를 사용할 수 없다. 이미 참여한 사람의 권한은 유지된다. 참여자를 제외하면 그 사람의 읽기·수정 권한을 제거하고 이전 초대 링크도 만료한다.

가입·초대 변경·제외는 여행 행을 잠그는 DB 트랜잭션으로 처리한다. 버전 조건부 UPDATE는 소유자/참여자 조건을 함께 검사한다. 여러 PM2 프로세스도 DB의 버전과 회원 테이블을 기준으로 동작한다. 별도 WebSocket·Redis·로드밸런서 설정은 필요하지 않다.

## 배포

프론트와 백엔드 둘 다 반영한다. 백엔드를 먼저 배포해 기존 앱의 읽기·저장과 호환되는 새 API를 연다.

- 백엔드: `routes/trips/repository.js`, `routes/trips/router.js` 변경 반영 후 기존 PM2 프로세스 재시작.
- DB: 첫 요청에서 두 테이블을 `CREATE TABLE IF NOT EXISTS`로 만든다. 운영 DB 계정에 테이블 생성 권한이 없다면 배포 담당자가 `D:/Backend/NoPlan/sql/20260918_trip_collaboration.sql`을 해당 DB에서 먼저 적용한다. 미리 만든 테이블에 읽기 권한이 있으면 CREATE 권한 거절을 처리하고 진행한다. 테이블 자체가 없거나 읽을 수 없다면 실패한다. 기존 데이터 삭제나 변경은 없다.
- 프론트: `npm run build` 결과 배포. `/app/trips/join`도 기존 SPA fallback으로 `index.html`에 도달해야 한다.
- 기존 로그인 쿠키 및 `CORS_ALLOWED_ORIGINS` 설정을 사용한다.
- `preview-*` 스크립트와 테스트용 메모리 DB는 운영 서버의 진입점에 등록하지 않는다.

이 PC에는 운영 전용 `config/db.js`가 없어 실제 MySQL/EC2에는 연결하지 않았다. 저장소의 SQL 경계를 메모리 DB로 대체한 통합 테스트를 수행했다. 배포 후 실제 서로 다른 계정으로 초대→가입→양쪽 수정→참여자 제외를 최종 확인한다.

## 확인 결과

- 백엔드 전체 554개 테스트 통과. 실제 라우터·저장소를 통한 인증, 비참여자 차단, 초대 생성·회전·만료, 재참가 중복 방지, 참가 인원 제한, 동시 저장의 200/409 분리, 권한 회수를 포함한다.
- 프론트 전체 18개 테스트 통과. 독립 필드 병합, 동시 추가, 순서 충돌, 삭제/수정 충돌, 충돌 후 새로고침 시 기준 버전 보존을 포함한다.
- 브라우저에서 서로 다른 두 샘플 사용자가 오전·오후 메모를 변경하고, 새로고침 없이 두 화면에 양쪽 변경이 모두 보이는 것을 확인했다.
- 추가 브라우저 검증은 도구의 자동 승인 검토에서 사용량 한도 초과로 중단되었다. 운영 로그인/OAuth 왕복과 실제 DB 배포 검증은 완료했다고 간주하지 않는다.

## 로컬 두 사람 테스트

백엔드 폴더에서 `node scripts/preview-trip-collaboration.cjs`를 실행한다. 프론트의 별도 PowerShell에서:

```powershell
$env:VITE_APP_API_URL='http://127.0.0.1:4320'
npm run dev -- --host 127.0.0.1 --port 5201 --strictPort
```

- 여행 만든 지민: `http://127.0.0.1:5201/dev-preview/trip-collaboration.html`
- 친구 서연: `http://localhost:5201/dev-preview/trip-collaboration.html`

서로 다른 브라우저 origin을 두 샘플 사용자로 구분한다. 실제 API 라우터·저장소·편집 컴포넌트를 사용하지만 로그인 식별과 DB만 테스트용이다. 두 샘플은 미리 같은 여행에 참여되어 있다. 메모리 데이터이므로 서버 재시작 시 초기화된다. 이 샘플 인증 방식을 운영에 사용하지 않는다.
