# 코스 추천 정확도 개선 — 2026-09-16

## 적용 범위

프론트 `generateCourse`와 백엔드 `/api/course/generate/generate-course`를 `requested-combinations-v2`로 연결했다. 모바일 빠른 추천·채팅 조건 확인, PC 여행 구간 추천에 적용한다. 별도의 기존 legacy 생성 엔드포인트는 이번 전환 대상이 아니다.

## 입력과 결과

- 선택한 활동을 최대 3개까지 모두 포함해야 성공한다. 심야 식사+술집도 2개 활동으로 보존한다. 산책·카페 자동 추가 및 한 활동만 남긴 부분 성공은 하지 않는다.
- 조건 확인에서 전체 1인 예산(제한 없음 포함), 정확한 인원, 주류 선호·주문량, 제외 음식 업종을 받는다. PC에서는 새로 추가할 구간의 예산이다.
- 성별·나이 대신 직접 고른 취향과 예산을 사용한다. 인원은 비용 나누기와 명확한 2인 이상 제약 등에 반영하며, 미확인 좌석 수용 인원은 보장하지 않는다.
- 로그인 사용자 기본 취향 저장은 해당 계정의 이 브라우저 localStorage에만 저장한다. 계정 서버 동기화가 아니며 인원은 매번 확인한다.
- 채팅 추출 스키마에 근거 문장을 가진 추가 활동을 넣어 복수 활동을 보존한다. 추출 실패 시 기존 단순 파서는 여전히 제한적이므로 조건 확인 화면에서 활동을 확인한다.
- 영업시간 미확인 장소는 기본 제외한다. 명시적으로 허용하면 미확인 표시를 붙인다. 휴무·폐업·품질 탈락은 허용 옵션과 무관하게 제외한다.
- 결과에 필수 활동 충족 수, 장소별·전체 1인 예상 가격, 영업 확인 상태와 이동 추정 여부를 표시한다. 미확인 가격은 0원으로 표시하지 않는다.

## 비용과 조합 탐색

기존 메뉴에서 대관·사무실·기간권·중량 단가·이상 가격 등을 제외한다. 음식은 1인분, 카페는 음료와 디저트 범위, 술집은 공유 안주와 선택 주류 주문량으로 추정한다. 가격의 25~75 분위 범위와 상단 15% 여유를 사용한다. 실제 주문 총액 보장이 아니다. 와인 등 병/잔 구분이 불명확하면 비용을 계산하지 않는다. 놀거리·산책의 비용 자료는 현재 자동 계산하지 않는다. 금액 제한이 있으면 비용 미확인 장소를 제외하고, 제한 없음에서는 미확인으로 표시한다.

활동별 상위 14개 후보를 모아 최대 40개 조합을 유지하는 제한된 조합 탐색을 수행한다. 시간·도보 거리·전체 예상 예산·세부 활동 조건을 확인한 뒤 최대 12개 완성 조합의 실제 이동/영업을 확인한다. 전체 후보에 대한 최적해 보장은 아니다. 기본 영업 검증 예산은 최소 25초이며 기존 환경변수의 더 큰 값은 유지한다. 프론트 요청 제한은 55초다.

Google 도보 경로를 받으면 실제 이동 시간으로 도착 시각을 다시 계산하고 영업과 종료 시각을 재검증한다. 경로가 없으면 보수적인 직선거리 기반 도보 추정을 표시한다. 영업은 체류 전체를 확인해 중간 휴게시간도 제외하고, 먼 미래 날짜에는 이번 주 임시 영업시간을 재사용하지 않는다.

미검증 단일 교체 후보를 반환하지 않는다. 다른 장소를 원하면 조건을 바꾸거나 전체 코스를 다시 추천받아 시간·예산을 다시 확인한다.

## 배포와 검증

프론트와 백엔드 모두 배포한다. 이번 변경으로 추가할 SQL·테이블·환경변수는 없다. 기존 Google Places/Routes 설정을 사용한다. 기존 공유사무실·스터디카페 제거 및 재수집 차단 변경도 작업 트리에 함께 있으므로 누락하지 않는다. 이번 알고리즘 작업은 실제 운영 DB 추가 수정이나 대량 외부 API 수집을 수행하지 않았다.

자동 검증: 백엔드 단위·실제 라우트 핸들러 통합 테스트, 프론트 TypeScript/빌드 및 변경 파일 ESLint. 브라우저에서 360/390/1440px 가로 넘침, 입력 검증, 요청 조건 전달, 실제 새 조합 엔진을 이용한 2개 장소 결과/예산 부족 흐름을 확인했다. DB·Google 응답은 fixture로 대체했으므로 운영 API 성공률 측정은 별도다.

수동 확인 예시:

1. 성수/건대, 20:30~다음 00:30, 친구 2명, 맛집+술, 1인 5만 원: 2개 활동이 모두 포함되거나 명확한 부족 이유가 나오는지 확인.
2. 같은 조건 2만 원: 비싼 코스를 그대로 반환하지 않는지 확인.
3. 술 취향/음식 업종 제외를 바꾸어 결과 확인.
4. 카페를 선택하지 않은 심야 요청에 카페·산책이 자동 추가되지 않는지 확인.
5. 영업시간 미확인 허용을 켰을 때 미확인 표시가 유지되는지 확인.

정확한 예약·좌석, 라스트오더, 현재 메뉴 가격은 아직 보장하지 않는다. 현재 자료 부족으로 추천 실패가 늘 수 있으며, 이때 실패 메시지와 입력 조건으로 다음 보완 지점을 판단한다.

## 건대 일식·포차 예산 실패 후속 수정

사용자 조건: 지금~밤까지, 두명/연인, 일식+포차, 소주 1인 2주문, 해산물 업종 제외, 도보 짧게. 운영 로그의 checks=0 및 price_unknown=7을 확인하고 설정된 DB를 읽기 전용으로 조회했다. 소주라는 일반명 대신 `진로골드 5,000원`처럼 브랜드만 등록된 메뉴를 인식하지 못하는 문제가 있었다. 실제 저장 가격을 사용해 브랜드명 소주를 분류하도록 수정했다. 가격이 아예 없는 장소의 가격을 임의로 채우지는 않는다.

기존에는 중간 후보 하나라도 budget/price_unknown으로 탈락하면 전체 실패를 예산 탓으로 설명했다. 활동별 가격 자료 부족/예산 초과/취향 후보 부족과 조합 단계의 도보·시간·총예산 실패를 구분하도록 수정했다. 로그에 정규화된 예산·주류·제외 업종, 활동별 후보 통과 수와 조합 단계별 탈락 수를 기록한다. 실패 화면에서도 예산과 주류·제외 업종 조건을 확인할 수 있다. 출발지 placeholder는 `예: OO역, OO동`으로 수정했다.

조회한 건대 장소·메뉴 스냅샷과 근사 출발 좌표로 재현할 때 수정 후 10만 원은 가격·동선 조합을 통과했다. 3만 원은 현재 가격을 계산할 수 있는 후보 및 도보 조건의 조합이 부족했다. 이 재현은 영업 응답을 테스트 값으로 대체했으므로 실제 영업/운영 전체 성공을 뜻하지 않는다. 백엔드 292개 테스트, 프론트 빌드 및 변경 화면 ESLint 통과. 두 서버 배포가 필요하며 추가 SQL·환경변수는 없다.

### 주류 분류 공통화 후속 수정

`alcoholMenus.js`에서 소주·맥주·와인·하이볼/칵테일·기타 주류를 함께 분류한다. 일반명, 등록된 한글/영문 브랜드·칵테일 이름 별칭, 명시적 메뉴 카테고리를 사용하며 취향 필터와 비용 계산이 같은 결과를 사용한다. 카스·테라·켈리·하이네켄, 산토리/버번 위스키 하이볼, 모히또·마가리타, 샤르도네 등의 회귀 사례를 추가했다. 임의의 모든 브랜드/시그니처 이름을 인식하는 모델은 아니며 별칭과 분류 데이터는 확장할 수 있다.

무알콜 음료, 카스테라·테라스 같은 동명 단어, 주류를 재료로 쓴 음식은 술로 분류하지 않는다. 와인·위스키 등의 잔/병/용량 단위가 없으면 비용 미확인으로 유지하고 명시된 병 가격은 병 주문 가격으로 사용한다. 안주+술 세트나 묶음 주류를 한 잔 가격으로 계산하지 않는다. 실제 가격을 새로 생성하거나 DB에 기록하지 않는다.

네 가지 주류 취향과 상관없음 선택의 플래너 통합 테스트 포함, 백엔드 총 300개 테스트 통과. 이번 주류 공통화는 백엔드 배포 대상이다.
