## 1. 제품 목표와 현재 방향

NoPlan은 사용자가 출발지, 시간, 동행, 목적, 이동 선호를 고르면 서울의 실제 방문 가능한 장소로 코스를 구성하는 서비스다.

현재 핵심 방향은 다음과 같다.

1. 서울 전역의 장소를 행정동·격자 기반으로 사전 수집한다.
2. 음식점, 카페, 놀거리, 문화/전시, 산책/구경, 술/야간을 서비스용 카탈로그에 저장한다.
3. 추천 시 사용자의 정확한 목적, 동행, 시간대, 분위기, 실제 이동 거리, 영업 상태를 함께 반영한다.
4. 부적절한 장소는 관리자 검수 또는 공통 제외 정책으로 추천에서 영구 차단한다.
5. 관리자용 카카오맵에서 서울의 비식당·비카페 장소를 빠르게 눈으로 검수한다.

## 2. 장소 데이터 구조에서 꼭 알아야 할 점

### 서비스 대분류

- `food`: 맛집
- `cafe`: 카페/디저트
- `activity`: 놀거리와 문화/전시의 실제 DB 저장 타입
- `hotplace`: 산책/구경
- `drink`: 술/야간

### 문화/전시의 특수 저장 방식

문화/전시는 DB에 `primary_type='culture'`로 저장되지 않는다. 다음처럼 저장된다.

- `primary_type='activity'`
- `detail_type`이 아래 중 하나면 문화/전시로 취급한다.
  - 전시
  - 영화
  - 공연
  - 팝업
  - 미술관/박물관
  - 독립서점
  - 복합문화공간

따라서 화면이나 통계를 만들 때 `primary_type`만 세면 문화/전시가 0으로 나오고 놀거리에 합산되는 버그가 생긴다. 관리자 지도 API는 현재 이 값을 가상 `culture` 타입으로 분리해서 반환한다.

### 산책/구경의 타입 제한

산책/구경은 `hotplace`만 사용한다. 일반 `activity`를 섞으면 노래방, 방탈출, 보드게임장, 통신 대리점 같은 곳이 산책 코스에 들어갈 수 있기 때문이다.

### 공급량 기반 목표

고정 수량만 채우지 않고 지역 공급량에 따라 목표가 달라지는 밀집도 정책을 사용한다.

- 강남·홍대처럼 공급이 많은 지역은 더 많이 확보한다.
- 상봉1동처럼 실제 공급이 적은 지역은 억지로 동일 수량을 채우지 않는다.
- 음식점은 동별·소분류별 목표를 계산한다.
- 문화/전시와 산책/구경은 희소성을 고려해 구 단위 목표와 세부 유형 분산을 사용한다.
- 후보 검증은 동과 소분류를 번갈아 처리해 한 지역·한 분류 쏠림을 줄인다.

### 품질 기준

식음료는 대체로 다음 완화 순서를 사용한다.

1. A: 평점 3.5 이상, 리뷰 10개 이상
2. B: 평점 3.0 이상, 리뷰 10개 이상
3. C: 그보다 낮더라도 리뷰 25개 이상인 후보

놀거리·문화·명소는 식음료와 같은 평점/리뷰 조건을 강제하지 않는다.

- 문화/전시와 산책/구경은 네이버 리뷰가 없더라도 카카오 원본 업종이 명확하면 승인 가능하다.
- 확인된 저평점은 제외할 수 있지만, 평점 자체가 없다는 이유만으로 공원·전시·문화시설을 버리지 않는다.
- 통신 대리점, 편의점, 주차장, 미용실, 일반 상점 등은 이름에 공원·랜드마크 같은 단어가 있어도 제외한다.

### Apify 관련 운영 원칙

- 카카오 무료 검색은 발견/사전조사에 활용한다.
- 상세 품질과 네이버 리뷰·메뉴 검증에 Apify를 쓴다.
- Actor 요청은 배치 및 동시 실행으로 처리한다.
- 공용 비용 상한을 넘지 않도록 예약 비용과 실제 비용을 분리 계산한다.
- 중간 종료 후 같은 명령을 재실행해도 기존 DB·캐시·실패 기록을 활용해 이어서 보강하도록 설계돼 있다.

## 4. 코스 추천 알고리즘에 반영된 정책

### 목적 정확도

- 사용자가 직접 고른 소분류는 넓은 대분류로 임의 대체하지 않는다.
- 예: 베이커리 요청을 일반 디저트 카페로 자동 대체하지 않는다.
- 요청 업종 밖 후보는 코스와 교체 후보 모두에서 제외한다.
- 맛집+산책 요청의 산책 슬롯은 반드시 `hotplace`다.

### 코스 순서와 전후 맥락

- 맛집과 술집을 함께 고르면 음식점 → 술집 흐름을 우선한다.
- `맛집 아무거나 + 포차`처럼 세부 음식이 비어 있으면 뒤의 포차와 어울리는 단체 식사를 우선한다.
- 사용자가 고기를 직접 골랐다면 전후 조합 점수로 다른 음식으로 바꾸지 않는다.
- 고기와 포차를 고르면 각각 한 번만 배정한다.
- 술집 뒤에 다시 갈비집 같은 식당을 넣지 않는다.
- 연결할 적절한 장소가 없으면 같은 업종을 억지로 반복하지 않고 짧은 코스를 반환한다.

### 빈 슬롯 처리

- 중간 코스가 검증 실패로 빠지면 뒤 일정을 앞으로 당긴다.
- 예: 음식점 → 산책 → 술집에서 산책 후보가 없으면 음식점 → 술집이 된다.
- 뒤 코스를 버리지 않고 가능한 일정으로 압축한다.
- 사용자가 버그로 오해하지 않도록 노피가 거리 조건·영업 검증 등 실제 제외 이유를 안내한다.

### 시간대 정책

39개 카탈로그 소분류에 명시적인 권장 시간대 정책이 있다.

- 고기, 술집 등은 저녁·야간 적합도를 높인다.
- 브런치는 늦은 시간에 감점한다.
- 전통시장과 상권은 서로 다른 피크 시간을 쓴다.
- 야경은 고정 시각이 아니라 서울의 계절별 일몰 시각을 따른다.
- 시간대는 기본적으로 소프트 점수이며 사용자가 직접 선택한 세부 목적을 시간만으로 제거하지 않는다.

### 문화/전시 0개 버그와 수정

처음에는 API가 `primary_type='culture'`를 찾았기 때문에 문화/전시가 0으로 표시됐다. 실제 운영 DB에는 문화 장소가 `activity + 문화 detail_type`으로 저장돼 있었다.

수정 당시 운영 DB 확인값:

- 전체 비식당·비카페 활성 장소: 10,465곳
- 놀거리: 3,052곳
- 문화/전시: 1,278곳
- 산책/구경: 1,621곳
- 술/야간: 4,514곳

이 수치는 관리자 검수를 진행하면 대기 목록에서 빠지므로 감소한다.

### 승인/제거 동작

DB 컬럼:

- `map_review_status`: `pending`, `approved`, `removed`
- `map_reviewed_by`
- `map_reviewed_at`

동작:

- 승인
  - `map_review_status='approved'`
  - `is_active=1` 유지
  - 노플랜 추천에는 계속 사용
  - 관리자 지도 검수 대기 목록에서는 즉시 제거
- 제거
  - `map_review_status='removed'`
  - `is_active=0`
  - 연결된 후보가 있으면 후보도 `rejected` 처리
  - 관리자 지도와 노플랜 코스 추천에서 모두 제외
  - 재수집/재승인 upsert가 실행돼도 `removed` 장소는 자동 재활성화하지 않음
- 모든 판정은 `noplan_place_admin_events`에 관리자와 함께 기록

API:

- `GET /api/admin/places/map`
  - 기본적으로 `is_active=1 AND map_review_status='pending'`
  - 음식점·카페 제외
- `POST /api/admin/places/map/:id/review`
  - body: `{ "action": "approve" }` 또는 `{ "action": "remove" }`

### 배포 시 스키마 처리

`ensurePlaceCatalogSchema()`가 기존 DB에 필요한 컬럼과 인덱스를 자동 추가한다.

- `map_review_status`
- `map_reviewed_by`
- `map_reviewed_at`
- `idx_noplan_place_map_review`

기존 장소는 기본값 `pending`으로 시작하므로 최초에는 모두 지도 검수 대상이다.

## 6. 보안 관련 현재 상태

과거 발견된 주요 문제는 평문 비밀번호, 프론트가 보낸 `userId` 신뢰, 세션 부재, 유료 API 요청 제한 부재였다.

현재 테스트로 확인되는 구현:

- 비밀번호 해시 저장 및 기존 평문 비밀번호 점진 업그레이드

### 2단계: 관리자 지도 스모크 테스트

테스트해도 되는 장소를 정한 뒤 다음을 확인한다.

   - 마커와 대기 개수가 즉시 감소해야 한다.
   - `noplan_places.is_active=0`이어야 한다.
   - 같은 지역·목적 코스 추천에 더 이상 나오지 않아야 한다.
3. 서버 재시작/새로고침 후에도 두 판정이 유지돼야 한다.

### 3단계: 후속 관리자 기능 후보

1. 구·동 필터 추가

## 10. 아직 남은 제품·데이터 과제

### 서울 카탈로그 완성도 감사

서울 전역 데이터가 많이 쌓였지만 다음을 한 번에 감사하는 리포트가 필요하다.

- 25개 구 × 6개 대분류 활성 개수
- 행정동별 0개 또는 비정상적으로 적은 분류
- 수집은 됐지만 메뉴가 없는 식음료 장소
- 문화/전시와 산책/구경 오분류
- 폐업·테이크아웃 전문·편의점 잔존 여부

과거 대화의 수집 완료 표만 믿지 말고 현재 운영 DB에서 다시 집계해야 한다.

### 관리자 지도 UX

현재 지도는 서울 전체 대기 장소를 한 번에 보여 주고 클러스터링한다. 실제 검수 속도를 높이려면 구별 진행과 판정 이력 조회가 필요하다.

### 분위기·가격대·연령 맥락

네이버 리뷰 태그 기반 분위기 점수는 들어갔지만, 예쁜 곳이 비싼 곳으로 치우치는 문제는 완전히 해결된 것이 아니다.

후속 기획 후보:

- 나이를 직접 묻기보다 `가볍게 / 적당히 / 제대로` 같은 예산·분위기 선택
- 사용자 프로필에 선택적 가격 선호 저장
- 코스 전체 예상 가격대 균형
- 비싼 장소만 연속 배치되지 않도록 코스 단위 페널티

### 산책/구경 품질

어린이공원과 일반 근린공원이 모두 나쁜 것은 아니지만, 목적과 동행에 따라 가치가 다르다.

- 산책 단독 요청: 규모, 산책 길이, 경관, 리뷰 태그 우선
- 식사 후 짧은 산책: 가까운 소공원도 허용
- 데이트: 야경, 수변, 테마거리, 복합문화공간 가산
- 친구: 시장/상권, 구경거리, 행사성 공간 가산
