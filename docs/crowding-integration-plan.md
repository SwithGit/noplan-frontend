# NoPlan 홍대 주변 혼잡도 연동 기획서

- 문서 상태: 개발 전달용 초안
- 작성일: 2026-08-08
- 적용 서비스: NoPlan 홍대 MVP
- 대상 저장소
  - Frontend: `D:\VSCode\NoPlan\noplan-web`
  - Backend: `D:\Backend\NoPlan`

## 1. 결정 사항

NoPlan에 혼잡도 정보를 도입한다. 이번 기능에서 필요한 것은 특정 매장 안의 정확한 인원수가 아니라, 추천 장소 주변이 현재 얼마나 붐비는지 보여주는 것이다.

1차부터 3차까지는 서울시 실시간 인구데이터를 사용한다. 4차에서는 SKT/TMAP 장소 혼잡도 무료체험으로 NoPlan 장소 DB와의 실제 매칭률을 조사한다.

표시 원칙은 다음과 같다.

- 서울시 권역 데이터는 `주변 혼잡도`라고 표시한다.
- SKT 또는 제휴 매장에서 특정 장소 단위 데이터를 확보한 경우에만 `매장 혼잡도`라고 표시한다.
- 정확한 인원수는 사용자 화면에 표시하지 않는다.
- `여유`, `보통`, `약간 붐빔`, `붐빔`, `정보 없음`의 단계만 사용한다.
- 통신 데이터 기반 추정치이므로 확정적인 표현을 사용하지 않는다.
- 혼잡도는 추천 실패를 일으키는 필수 필터가 아니라 정보 표시와 소프트 점수로 사용한다.

## 2. 목표와 제외 범위

### 목표

- 홍대 권역의 현재 주변 혼잡도를 결과 화면에서 확인할 수 있다.
- 사용자가 `대기 적게`를 선택했을 때 상대적으로 덜 붐비는 권역의 장소를 우선한다.
- 외부 API 장애나 데이터 누락이 발생해도 코스 생성은 정상적으로 완료된다.
- 외부 API 키를 프론트에 노출하지 않는다.
- SKT/TMAP 무료체험으로 개별 장소 또는 상권 데이터의 실사용 가능성을 판단한다.

### 이번 범위에서 제외

- 비홍대 지역 지원
- 특정 매장 내부의 정확한 인원수 표시
- 모든 카페와 식당의 실제 좌석 점유율 추정
- 혼잡도 입력 단계를 새로 추가하는 것
- 혼잡한 장소를 무조건 추천에서 제외하는 것
- SKT/TMAP 유료 상품 즉시 계약
- 장기간 원천 혼잡도 데이터를 무제한 적재하는 것

## 3. 데이터 공급원

### 3.1 서울시 실시간 인구데이터

1차 적용의 기본 데이터다.

- 약 5분 단위로 갱신되는 실시간 인구 및 혼잡 단계 제공
- 서울시 주요 121개 장소 중 한 장소를 장소명 또는 코드로 조회
- Open API 인증키 필요
- 공공누리 1유형으로 출처표시 시 상업적 이용 및 변경 가능
- 정확한 현장 인원수가 아니라 통신사 신호를 가공한 추정 데이터

홍대 MVP에서 사용할 우선 권역:

### 3.2 SKT/TMAP 장소 혼잡도

4차 검증용 데이터다.

공식 상품에는 다음 기능이 안내되어 있다.

- 데이터 제공 가능 장소 및 상권 목록
- 실시간 장소 혼잡도
- 실시간 상권 혼잡도
- 시간대별 및 통계성 혼잡도
- 방문자 통계

중요한 제약:

- 임의의 좌표를 입력하면 모든 매장의 혼잡도가 나오는 상품으로 간주하면 안 된다.
- 먼저 SK가 제공하는 장소 및 상권 목록과 NoPlan DB를 매칭해야 한다.
- 장소명만 같다고 매칭하지 않고 이름, 좌표, 주소를 함께 비교한다.
- SK 데이터가 없는 장소에는 서울시 권역 혼잡도를 fallback으로 사용한다.

공식 자료:

- SK Open API 장소 혼잡도: https://openapi.sk.com/products/detail?svcSeq=56
- 장소 혼잡도 요금: https://openapi.sk.com/products/calc?menuSeq=263&svcSeq=56
- TMAP API 요금: https://openapi.sk.com/products/calc?menuSeq=5&svcSeq=4

## 4. SKT/TMAP 무료체험으로 확인 가능한 범위

2026-08-08 공식 공개 페이지 기준으로 서로 다른 상품 진입 경로에 다음 무료 한도가 표시된다.

| 상품 경로 | 공개된 무료 한도 | 유료 전환 참고 |
|---|---:|---|
| SK Open API `장소 혼잡도` Free | 월 10건 | Basic은 공식 페이지상 건별 과금 안내 |
| TMAP Free 내 `Puzzle 장소 혼잡도` | 일 3건 | 공식 TMAP 요금 페이지상 Basic 건별 과금 안내 |

실제 계정에서 선택한 상품, API 버전 및 계약 상태에 따라 적용 한도가 다를 수 있으므로 앱 등록 후 대시보드의 최종 한도를 다시 확인한다.

### 무료체험 판단

- 월 10건만 제공되는 경로라도 API 연결 여부와 홍대 데이터 존재 여부를 검증하는 PoC는 가능하다.
- 지속적인 실시간 서비스 운영에는 무료 한도가 부족하다.
- 장소 목록 API로 홍대 지원 장소를 한 번에 충분히 가져올 수 있다면, 목록을 로컬에서 NoPlan DB와 대조하여 호출을 절약할 수 있다.
- 장소 목록도 페이지별로 과금되거나 호출량에 포함될 수 있으므로 실제 응답과 대시보드 사용량을 함께 기록한다.

### 월 10건 기준 권장 테스트 배분

| 사용량 | 테스트 내용 |
|---:|---|
| 1~2건 | 데이터 제공 가능 장소 또는 상권 목록에서 홍대 검색 |
| 3~5건 | 매칭된 대표 장소 3곳의 실시간 혼잡도 조회 |
| 6~7건 | 같은 장소를 다른 시간에 재조회하여 갱신 여부 확인 |
| 8건 | 지원되지 않는 NoPlan 장소 조회 시 오류 또는 빈 응답 확인 |
| 9건 | 상권 단위 홍대 조회 가능 여부 확인 |
| 10건 | 응답 필드, 기준 시각, 장애 fallback 최종 재검증 |

TMAP 경로에서 일 3건이 제공되는 경우에는 위 테스트를 여러 날에 나누어 실행한다. 무료체험 단계에서 전체 DB 장소를 하나씩 실시간 조회하지 않는다.

### 4차 통과 기준

다음 조건을 모두 기록하고, 유료 전환 여부는 별도로 결정한다.

- 홍대 또는 연남동 상권 데이터 제공 여부
- NoPlan 승인 장소 중 SK 지원 장소 매칭 개수와 비율
- 장소 단위와 상권 단위 응답의 차이
- 응답 갱신 시각과 실제 갱신 간격
- 한 요청이 차감하는 호출량
- 장소 목록 API의 페이지당 차감 여부
- 예상 일간 호출량과 월간 비용

권장 유료 검토 기준:

- 홍대 상권 조회가 안정적으로 가능하거나,
- NoPlan 핵심 추천 장소의 의미 있는 비율이 장소 단위로 매칭되고,
- 서울시 권역 데이터보다 사용자에게 명확한 추가 가치를 제공하는 경우

매칭률이 낮으면 SKT 유료 전환 없이 서울시 권역 혼잡도만 유지한다.

## 5. 공통 혼잡도 데이터 모델

외부 공급자별 응답을 프론트에 그대로 전달하지 않고 백엔드에서 다음 형식으로 정규화한다.

```ts
type CrowdingLevel =
  | 'relaxed'
  | 'normal'
  | 'busy'
  | 'very_busy'
  | 'unknown';

interface CrowdingSnapshot {
  scope: 'area' | 'place';
  source: 'seoul' | 'skt' | 'merchant' | 'unknown';
  areaCode?: string;
  areaName?: string;
  providerPlaceId?: string;
  level: CrowdingLevel;
  label: '여유' | '보통' | '약간 붐빔' | '붐빔' | '정보 없음';
  message: string;
  observedAt?: string;
  fetchedAt: string;
  stale: boolean;
}
```

서울시 응답의 인구 최소/최대값은 내부 판단에 사용할 수 있지만 이번 사용자 화면에는 노출하지 않는다.

## 6. 장소와 혼잡 권역 매핑

각 승인 장소에 혼잡도 권역 코드를 연결한다.

권장 필드:

```text
crowding_area_code
crowding_area_name
crowding_provider_place_id
```

구현 원칙:

1. 서울시가 제공하는 주요 장소 영역 파일을 기준으로 장소 좌표가 포함되는 권역을 계산한다.
2. 세부 권역이 겹치면 `연남동`, `홍대입구역`, `합정역`을 `홍대 관광특구`보다 우선한다.
3. 어떤 세부 권역에도 명확히 속하지 않지만 홍대 서비스 범위 안이면 `POI007`을 사용한다.
4. 관리자 화면에서 자동 매핑 결과를 확인하고 수정할 수 있게 하는 것은 후속 개선으로 둔다.
5. 첫 MVP에서는 마이그레이션 또는 안전한 배치 작업으로 기존 홍대 승인 장소에 코드를 채운다.

한 장소에 서울시와 SKT 데이터가 모두 있으면 표시 우선순위는 다음과 같다.

```text
신뢰 가능한 제휴 매장 직접 정보
→ SKT 장소 단위 정보
→ 서울시 권역 정보
→ 정보 없음
```

## 7. 단계별 개발 범위

### 1차: 서울시 주변 혼잡도 백엔드 연동

개발 내용:

- 서울시 Open API 키를 서버 환경변수로 관리
- 서울시 응답을 `CrowdingSnapshot`으로 정규화
- 홍대 권역 코드별 조회 기능 구현
- 동일 권역 응답을 5분 캐시
- 외부 API timeout 적용
- 최근 정상 데이터가 있으면 장애 시 최대 30분 동안 `stale: true`로 반환
- 최근 데이터도 없으면 `unknown` 반환
- 외부 API 장애가 코스 생성 실패로 이어지지 않게 처리
- API 키, 전체 원본 응답 및 민감한 오류 내용을 프론트로 전달하지 않음

권장 환경변수:

```text
SEOUL_OPEN_DATA_KEY=
CROWDING_SEOUL_ENABLED=true
CROWDING_CACHE_TTL_MS=300000
CROWDING_STALE_TTL_MS=1800000
CROWDING_REQUEST_TIMEOUT_MS=3000
```

완료 조건:

- 4개 홍대 권역을 각각 조회할 수 있다.
- 서울시 단계가 내부 공통 단계로 정상 변환된다.
- API 장애, timeout, 잘못된 응답에서 `unknown` 또는 stale 데이터가 반환된다.
- 인증키가 프론트 번들 및 로그에 노출되지 않는다.
- 캐시로 인해 같은 권역을 장소 카드마다 반복 호출하지 않는다.

### 2차: 프론트 혼잡도 표시

표시 위치:

- 코스 결과 장소 카드
- 코스 지도 또는 장소 상세 화면

표시 예시:

```text
연남동 주변 · 약간 붐빔
18:35 기준 · 서울시 실시간 인구
```

UI 원칙:

- `scope: area`는 반드시 `주변 혼잡도` 또는 `OO 주변`이라고 표기
- `scope: place`만 `매장 혼잡도`라고 표기
- 정확한 인원수는 표시하지 않음
- 기준 시각과 출처 표시
- stale 데이터는 `최근 확인` 등의 표현으로 구분
- unknown이면 공간을 억지로 채우지 않고 `혼잡도 정보 없음` 또는 미표시
- 혼잡도 때문에 입력 단계를 추가하지 않음
- 색상만으로 상태를 전달하지 않고 텍스트 라벨을 함께 표시

완료 조건:

- 여유, 보통, 약간 붐빔, 붐빔, 정보 없음 상태가 깨지지 않고 렌더링된다.
- 지역 데이터가 매장 내부 정보처럼 오해되지 않는다.
- 모바일 화면에서 장소명, 시간, 혼잡도 라벨이 겹치지 않는다.

### 3차: `대기 적게` 추천 점수 반영

현재 조건 조정 옵션인 `대기 적게`를 재사용한다. 새 입력창이나 필수 질문을 추가하지 않는다.

반영 원칙:

- `대기 적게`를 선택하지 않았으면 혼잡도는 기본적으로 정보 표시만 한다.
- `대기 적게`를 선택하면 혼잡 단계에 따라 소프트 감점을 적용한다.
- 혼잡도 정보가 없다는 이유로 후보를 제외하지 않는다.
- 영업 여부, 핵심 목적 적합도, 슬롯 유지가 혼잡도보다 우선한다.
- 모든 후보가 같은 권역이면 혼잡도 점수 때문에 순위가 인위적으로 달라지지 않게 한다.
- 데이터가 stale이면 감점 강도를 낮춘다.

초기 감점 예시이며 실제 상수는 설정 가능하게 둔다.

| 단계 | 기본 | `대기 적게` 선택 |
|---|---:|---:|
| 여유 | 0 | 0 |
| 보통 | 0 | -2 |
| 약간 붐빔 | 0 | -6 |
| 붐빔 | 0 | -10 |
| 정보 없음 | 0 | 0 |

완료 조건:

- `대기 적게` 선택 시 덜 붐비는 서로 다른 권역 후보가 우선될 수 있다.
- 혼잡한 후보밖에 없어도 코스 슬롯이 사라지지 않는다.
- 혼잡도 API 장애 시 기존 추천 결과와 동일하게 생성된다.
- 진단 정보에 혼잡도 소스, 단계 및 적용 감점을 남긴다.

### 4차: SKT/TMAP 무료체험 및 매칭률 조사

- SK Open API 계정 및 애플리케이션 생성
- 장소 혼잡도 또는 TMAP Puzzle 장소 혼잡도 무료 상품 신청
- 대시보드에서 실제 무료 호출 한도 확인
- 발급 키를 백엔드 환경변수로만 등록

## 8. 기존 기능과의 연결

현재 백엔드 `server.js`에는 `/api/update-status`와 메모리 기반 `storeLiveStatus`가 있고, 프론트 Supporters 화면에서 매장 상태와 혼잡도를 제보하는 초안이 존재한다.

이 기능은 현재 다음 한계가 있다.

- 서버 재시작 시 데이터 소실
- 조회 API와 추천 엔진 연결 없음
- 정보 제공자 및 갱신 시각의 신뢰성 정책 부족

이번 1~4차에서는 이 제보 기능을 혼잡도 주 공급원으로 사용하지 않는다. 다만 향후 제휴 매장용 `merchant` 소스로 통합할 수 있도록 공통 모델의 `source` 값만 준비한다.

## 9. API 및 캐시 권장 구조

```text
서울시 API / SKT API
        ↓
Backend crowding provider adapter
        ↓
정규화 + 5분 캐시 + stale fallback
        ↓
코스 생성 점수 / 결과 API
        ↓
Frontend 주변 혼잡도 표시
```

주의 사항:

- 장소 카드마다 외부 API를 직접 호출하지 않는다.
- 한 코스에 연남동 장소가 3곳 있어도 `POI073`은 캐시당 한 번만 호출한다.
- 코스 생성 요청의 응답 지연을 막기 위해 짧은 timeout을 사용한다.
- 혼잡도 조회 실패를 코스 생성 실패 사유로 사용하지 않는다.
- 원천 응답 장기 저장은 공급자 약관 검토 전 진행하지 않는다.

## 10. 테스트 시나리오

### 백엔드

- 서울시 `여유` 응답이 `relaxed`로 변환된다.
- 서울시 `보통` 응답이 `normal`로 변환된다.
- 서울시 `약간 붐빔` 응답이 `busy`로 변환된다.
- 서울시 `붐빔` 응답이 `very_busy`로 변환된다.
- 알 수 없는 라벨은 `unknown`으로 처리된다.
- 같은 권역을 연속 요청하면 외부 API는 한 번만 호출된다.
- timeout 시 코스 생성이 정상 완료된다.
- stale 허용 시간 안에는 최근 정상값이 반환된다.
- stale 허용 시간이 지나면 unknown이 반환된다.
- `대기 적게` 미선택 시 추천 점수에 감점이 없다.
- `대기 적게` 선택 시 서로 다른 권역 후보의 혼잡 단계에 따라 감점된다.
- 모든 후보가 혼잡해도 필수 슬롯은 유지된다.

### 프론트

- 주변 혼잡도와 매장 혼잡도 문구가 구분된다.
- 기준 시각과 출처가 표시된다.
- 데이터 없음과 stale 상태가 안전하게 표시된다.
- 혼잡 단계별 텍스트와 접근 가능한 상태 라벨이 있다.
- 모바일 장소 카드 레이아웃이 깨지지 않는다.

### SKT/TMAP PoC

- 지원 장소 목록을 조회할 수 있다.
- 홍대 또는 연남동 상권 존재 여부가 확인된다.
- NoPlan 장소와 동일 장소를 이름만이 아닌 좌표 및 주소로 검증한다.
- 무료 호출 사용 전후 대시보드 사용량을 기록한다.
- 데이터가 없는 장소는 서울시 권역 데이터로 fallback된다.

## 11. 개발 페이지 전달용 요청문

```text
Frontend D:\VSCode\NoPlan\noplan-web와 Backend D:\Backend\NoPlan을 먼저 읽고, 기존 사용자 변경을 보존한 상태에서 docs/crowding-integration-plan.md의 1차부터 순서대로 구현해줘.

현재 서비스 범위는 홍대이며 정확한 인원수는 표시하지 않는다. 서울시 데이터는 매장 혼잡도가 아니라 주변 혼잡도로 표시해야 한다. 외부 API 키는 백엔드 환경변수로만 관리하고, 혼잡도 API 장애가 코스 생성 실패로 이어지면 안 된다.

우선 이번 작업에서는 기획서의 1차 구현과 테스트를 완료하고, 2차 이후는 현재 코드와 API 응답을 기준으로 이어서 진행해줘. 작업 전 git status와 관련 코드를 확인하고 기존 미커밋 변경을 되돌리지 마라. 각 단계 완료 후 빌드와 테스트 결과, 남은 외부 준비사항을 보고해줘.
```
